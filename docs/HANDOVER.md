## 目的と方針(オーナーが決めたこと)
- DEX内で完結する原子的裁定bot。フラッシュスワップ+自作コントラクト。CEX裁定は対象外

## 現在の仕組み(2026年9月19日に書き直し。下の各節が経緯)

- V2の `Sync` / V3の `Swap` をWebSocketで受信し、メモリ上の地図で経路(2〜3段)を即判定
- **始点トークンは36種**。手書きの一覧に加え、V2で深さ$50,000以上のトークンを
  起動時に選んでV3プールを探す(`V3_DISCOVERY_TOKENS=40`)。価格は安定通貨から
  隣へ辿って逆算し、5分ごとに作り直す
- V3の見積もりは**価格表**(公式QuoterV2、フォークとAlgebraは自前の `quoteV3`)。
  ただし**作り置きはしない**(`QUOTE_TABLE_FILL_ALL=false`)。現在価格と深さで
  ふるいにかけ、**ガス代を引いて$0.01を超える候補が出た経路の段だけ**その場で
  作る。費用はプール数ではなく候補の数に比例する
- 価格表は作った時の価格つきで `/data` に保存し、起動時に**動いていない表だけ**戻す
- 価格表の作り直しは**累積のズレ**(3bps)で判定。送信直前に同じプールが2回
  赤字になったら、そのV2の手数料の前提(30bps)を捨てて45bpsに戻し、実測し直す
- 送信は「`simulateRoute`(eth_call)で正確な利益を確認 → `executeRoute`」。
  赤字と分かった経路は**段ごとに正確に見積もり直して犯人を名指し**し、
  プールが動くまで再判定しない
- 送信は**プール単位の錠**で並行(`NonceManager` が nonce を手元で管理、
  同時最大3本)。同じプールを使う経路だけ直列
- ガス代の見積もりは実測の gasUsed と実効単価から学習(上限は費用に数えない)
- コントラクトは新旧2版がある。新版(ガス削減版)には経路を `(pool, tokenOut, flags, feeBps)` で
  渡し、`flags` に「V3か」「投入通貨が token0 か」「getAmountOut を持つか」を bot が地図から
  入れる。旧版には従来の形で渡す。どちらかは起動後に `FLAG_V3()` で判別して覚える
- 最低利益 `MIN_PROFIT_USD=0.005`。取引上限$2000
- 30秒後に「誰が取ったか」を記録簿に残す。ダッシュボードの時刻は日本時間

## フォークのプールを見積もれない問題(2026年9月17日)

Uniswap公式の QuoterV2 は quoteExactInputSingle(tokenIn, tokenOut, fee) の形で、
引数にプールのアドレスが無い。中に固定されたファクトリーからアドレスを計算
するため、フォークのプールには届かない。
一方 legIsUsable() はV3の段に価格表を要求するので、価格表が作れないプールは
経路に使えない。これが次の全てに共通する根本原因だった。

- Polygon の RamsesX(V3 Swapの22.4%)
- Optimism の未監視ファクトリー(27プール)
- Base の未監視ファクトリー(18プール)

対策は「プールのアドレスを直接受け取る見積もり」。コントラクトに quoteV3 を
足し、QuoterV2 と同じくわざと失敗させて受取量を返す。コールバックは実行と
同じものを使うので、対応済みの形式(uniswapV3 / pancakeV3 / algebra)は
そのまま扱える。bot側は「公式で求まらなかった分だけ」自前に回すので、
既存の Uniswap プールの動きは変わらない。

有効化は環境変数 ENABLE_FORK_QUOTER にチェーン名をカンマ区切りで指定する。
未設定なら自前の見積もりは一切走らない。コントラクトに quoteV3 を入れて
再デプロイするまでは有効にしないこと。

### 公式Quoterへの振り分けは「フォークかどうか」で決める

当初この振り分けを「手数料帯を持つか」で書いていたが、これは危険な誤り
だった。フォークにも手数料帯を持つもの(Uniswap形式のフォーク)があり、
それを公式Quoterに投げると、公式側に同じペア・同じ手数料帯のプールが
ある場合に **別のプールの価格が返ってくる**。それをフォークのプールの
価格表として保存すると、存在しない価格差=幻の利益機会を作り出す。
今は isForkFactory() でファクトリー単位に判定している。一覧に無い
ファクトリーは公式と断定できないため、安全側(フォーク扱い)に倒す。

### ファクトリーの style は実測済み。確認すべきは書き写し

一度「style は未検証」と書いたが、これは誤りだった。調査スクリプトは同じ
ファクトリーに getPool と poolByPair の両方を allowFailure 付きで投げ、
実際に住所を返した方を採っている(pool-survey.js の probeFactoryForPairs)。
Base 18件 / Optimism 27件というプール数も、その反応から得た実データ。

残る不確かさは「調査結果を V3_FACTORIES へ書き写す作業」だけで、実際に
チェックサムの大文字小文字を3件書き間違えていた。そのため
discoverV3PoolsForChain は fork のファクトリーごとに発見件数を
`[発見] polygon algebra-a(algebra): V3プール○件` の形でログに出す。
**ENABLE_FORK_QUOTER を有効にした直後、この行が0件でないことを必ず確認する。**

なお作業用コンテナからは外部RPCへ出られない(ネットワークポリシーで遮断)ため、
アドレスの実在確認はこのログか、Railway上での実行でしか行えない。

## Algebra形式のプールへの対応(2026年9月18日に実施)

下の節で「まだ使えない」と書いた2点を直し、`ALGEBRA_SUPPORTED = true` にした。

1. **状態の読み取り** — `multicall-reserves.js` が `globalState()` に対応。
   返り値の並びは版によって違う(Algebra V1は7個、Integralは6個で中身も別物)
   ため、**ABIで丸ごと復号せず、共通する先頭2語(uint160 price / int24 tick)
   だけを自前で読む**。丸ごと復号すると版が違うだけで価格を取れなくなる。
   int24 は32バイトに符号拡張されて入るので、負のtickを戻す処理を入れてある。
   一度 globalState で読めたプールは覚えておき、次から slot0 を試さない
2. **WebSocketの購読** — 手数料を含む Algebra の Swap 識別子2種を追加した。
   `Swap(…,int24,uint24)` と `Swap(…,int24,uint24,uint24)`。
   先頭4つ(amount0/amount1/price/liquidity)の位置はどれも同じなので、
   復号は `decodeV3SwapData` をそのまま使える
3. **見積もり** — 自前の `quoteV3`。コントラクトは `algebraSwapCallback` を
   元から持っていたので、コントラクト側の変更は不要だった

このとき `dex-onchain-realtime.js` には **import が1つも無かった**。
ethers を使うには import の追加が要る(無いと起動時に ReferenceError で落ちる)。
あわせて、手書きしてあった識別子4件を `ethers.id()` の計算に変えた
(検算したところ4件とも正しかったが、手書きは過去の事故の原因そのものなので)。

PR #9 で algebra-a(Polygon、V3 Swapの22.4%)と algebra-b(Base)を

2. **WebSocketの購読**: `dex-onchain-realtime.js` の ALL_TOPICS は

### コントラクト確認で見たこと(再デプロイ前の手順)

`quoteV3` は通常の取引と同じコールバックを使い、中間の足も見積もりも
どちらも `data.length == 0` で入ってくる。区別は `quoting` フラグだけなので、
これが実取引に漏れると支払いの代わりに QuoteResult で巻き戻り、全取引が
失敗する。安全である根拠は次の3つ。

1. `quoting = true` を書くのは `quoteV3` だけで、`quoteV3` は必ず revert して
   終わる。書き込みは毎回巻き戻り、成功する取引の開始時点では必ず false
2. `quoteV3` には `require(!inFlashSwap)` があり、実行中には入れない
3. 実取引の1段目は data が空でないため、この分岐に来ない

## 「あと何bpsで黒字だったか」を測る(2026年9月18日に追加)

Polygonのカバー率を埋めたあとも、20分で18万回の経路計算に対して粗利が
プラスの経路は0件だった。つまり問題は「見えていないプールがある」ことから
「価格のズレが手数料の壁+ガス代を超えない」ことへ移っている。

利益が出る条件は `価格のズレ > 手数料の壁 + ガス代/投入額`。実測値を入れると:

| チェーン | 壁(最小) | ガス代 | $5投入時のハードル | $50投入時 |
|---|---|---|---|---|
| Polygon | 0.35% | $0.012 | 0.59% | 0.37% |
| Optimism | 0.06% | $0.005 | 0.16% | 0.07% |
| Avalanche | 未実測 | $0.001 | — | — |

HANDOVERに記録した実勢は「本物の価格差は投入額の0.1〜0.5%程度」なので、
Polygonのハードル0.59%は分布のほぼ上端にある。これが0件の理由。

そこで finalize が捨てる前に「一番良かった時の利回り(bps)」を記録し、
段階ごとに数える仕組みを入れた(opportunity-scanner.js の nearMiss)。
**RPCは一切増えない。findBestAmount がすでに計算した値を数えるだけ。**

生存ログの `[惜しい]` 行と、ダッシュボードの「あと何bpsで黒字だったか」で
見られる。`countIfWallDrops(chain, bps)` は「壁がbps下がったら何本が
粗利プラスへ変わるか」を返す(段をまたぐ分は数えないので少なめに出る)。

既定の比較幅は29bps(= Polygonの35bps − Optimismの6bps)。環境変数
WALL_DROP_BPS で変えられる。**Optimismへ移す判断は、この数字を見てから行う。**

### 最初の版の欠陥と、その修正(同日)

最初の版は**評価するたびに1件数えていた**。Polygonは21ペアしか無いのに
43分で50万回評価するため、同じ経路が何千回も数え直され、「+66件」が
66個の機会なのか1個を66回見たのかを区別できなかった。Avalancheで
「-20〜-10bpsに200件、隣の段は0件」という不自然な穴が出たのがその証拠。

今は**経路ごとに「今までで一番良かった利回り」だけを持つ**(routeBest)。
件数は「届きうる別々の経路の本数」になる。キーはチェーン+始点トークン+
プール列で、上限50,000件(NEAR_MISS_ROUTE_LIMIT)。

あわせて**壁の高さでも分けた**。手数料1%のプールを2段通れば壁は200bpsで、
価格がどれだけ動いても黒字にならない。こうした構造的に無理な経路が
Polygonでは99.4%を占め、届きうる経路の信号を埋もれさせていた。
既定では壁60bps以下(REACHABLE_WALL_BPS、0.3%+0.3%まで)に絞った分布を出す。

### 43分間の実測(修正前の版・回数ベース)

| チェーン | 評価した経路 | 粗利プラス | 壁が29bps下がれば |
|---|---|---|---|
| polygon | 504,369 | 17 | +66(4.9倍) |
| arbitrum | 135,752 | 152 | +1,206(8.9倍) |
| avalanche | 33,684 | 0 | +200 |

生存ログの「粗利プラス169」と分布の先頭段の合計(17+152+0=169)が一致し、
計測そのものは正しいことを確認した。

**ただし Arbitrum の数字は信用してはいけない。** ARBITRUM_WSS_URL が未設定で
受信0件、定期読み直しの古い価格で判定しているため、実在しない価格差が出る。
152本が粗利プラスと出ながら取引が1件も成立していないのがその裏付け。
**ARBITRUM_WSS_URL を設定するのが、いちばん安く情報量の大きい次の一手。**

### 投入額の上限を上げた(2026年9月18日)

上の「取引上限$2000は到達できない」への対応。ただし**価格表を伸ばすだけでは
逆効果**で、先に投入額の探し方を直す必要があった。

findBestAmount は投入額を**上限に対する比率**で探しており、最小が0.01だった。
上限$300なら$3から探せるが、価格表を$2000まで伸ばすと最小が$20になる。
**実測の最適額は$1.78〜$8.05で全て$20未満**のため、伸ばすと今できている
取引を取り逃す。検証では上限$2000のとき理想の60%の利益しか取れなかった。

そこで小さい側を対数的に細かく刻む比率に変えた(最小0.0005)。同じ検証で
上限$300/$1,000/$2,000のいずれでも理想の100%を取れることを確認した。
そのうえで QUOTE_SAMPLES_USD に 1000 と 2000 を足した。倍率は従来と同じ
約3倍を保っている(間隔を空けると点と点の間の補間が過大になるため)。

**効果があったかは hitCap で測る。** 生存ログの `粗利プラスN(上限張付M)` の
M が、投入額が上限の95%以上に張り付いた回数。**0のままなら上限は効いて
おらず、刻みを増やした分のRPCが無駄なので QUOTE_SAMPLES_USD を元に戻す。**

RPCの増加見積もり: 価格表の子呼び出しが 864/分 → 1,152/分、束ねた後で
約29/分 → 約38/分。全体では毎分84 → 約94、月末見込 8% → 約9%。

### (対応前の記録)取引上限$2000は到達できない

V3を含む経路の投入額は、価格表の最大点(QUOTE_SAMPLES_USD の $300)で
頭打ちになる(routeMaxAmountIn)。ダッシュボードの取引上限$2000は
V3を含む経路には効いていない。刻みを伸ばせば、同じ価格差でも利益が増え、
ガス代の比率が下がってハードル自体も下がる(Polygonで$5→$50なら
0.59%→0.37%)。findBestAmount が最適な額を探すので、上限を上げても
無理に大きくは張らない。

## 「壁が下がっていたら、いくら取れたか」の試算(2026年9月18日)

本数だけでは戦略の上限が分からないため、**金額**まで出せるようにした。
生存ログの `[試算]` 行と、ダッシュボードの表で見られる。

各サンプル額について「手数料が W bps 低ければ受取がその分増える」として
利益を計算し、経路ごとに一番良かった値を保持する。**simulateRoute の
呼び出しは増えないのでRPCは増えない。** 既定の W は 29 / 50 / 100
(環境変数 WHATIF_WALL_DROPS)。

100bps は現実には到達できない(Polygonの壁35bps、Optimism 6bps、差は29bps)。
**「壁を極限まで下げても $いくらにしかならない」という天井を測るための値。**

### この数字は必ず多めに出る

- 経路ごとの**最良の瞬間**だけを足している(同時に全部は取れない)
- 複数の経路が同じプールを共有していても別々に数えている。
  実際には1つの価格差は1回しか取れない
- 自分が取れば価格が動くが、その分を引けていない
- 競争を考慮していない。壁が低ければ他社も参入する

**期待できる金額ではなく、この戦略の天井として読むこと。**
天井が小さければ、それ以上の投資(チェーン追加・速度改善)は見合わない。

## 動いていた構成と、動かなくなった構成(2026年9月18日)

**成功した7件は全て9月17日以前**で、新コントラクトを入れた 00:24 UTC 以降は
取引が1件も成立していない。過去ログの `[判定の精度]` を全デプロイ分遡ると、
**送信直前まで進んだ6件すべてがチェーン上では赤字(精度 0/6 = 0%)**だった。

| | 成功した7件 | 失敗した6件 |
|---|---|---|
| 時期 | 9/17以前 | すべて9/18 |
| チェーン | Polygon のみ | Polygon 2 / Arbitrum 4 |

| 経路 | Uniswap + sync発見(V2) | algebra-a / arbitrum / 3段 |

失敗6件の実測誤差:

| 段数 | 誤差 |
|---|---|
| 2段(Arbitrum) | −3 〜 −14bps |
| **3段(Polygon)** | **−50 〜 −94bps** |

**誤差は経路の複雑さに比例して増える。** 狙う利幅は5〜50bpsなので、3段経路の
誤差(50〜94bps)は利幅を上回っている。**それは機会ではなくノイズ。**

### 考え方の誤り

動いていたものは「小さくて単純」だった(少数の実績あるプール、2段中心、
小さな投入額、PolygonのUniswap)。9月18日にプールを3倍にし、Algebraと
フォークを足し、新チェーンの受信を繋ぎ、3段経路を広げ、投入額を30倍にした。
**部品を足すたびに見積もりの誤差が積み上がり、動いていたものまで埋もれた。**

「機会が足りない」と考えて範囲を広げ続けたが、**広げるほど精度が落ちる**
という関係を見ていなかった。

### 進め方は逆向きにする

動いていた構成まで戻し、そこで精度を測り、**1つずつ足して毎回精度を測る**。
落ちたらその部品が原因。

### 見積もり誤差の測り方を直した

`verifyV3Calculations` は**$20でしか測っていなかった**。価格表の点は
$1,3,10,30,100,300,1000,2000 で、$20は「$10〜$30」という狭い区間にあり
補間の誤差が最も小さい場所。一方、実際に赤字と確定した取引は $102 と $276、
つまり「$100〜$300」という広い区間にある。**いちばん簡単な点だけを
測っていた。**

今は VERIFY_AMOUNTS_USD(既定 20,200,700)の各額で測り、**%ではなくbps**で
集計する(狙う利幅が5〜50bpsのため、1%=100bpsの閾値では粗すぎた)。
生存ログの `[見積もり誤差]` に投入額ごとの平均・最悪・過大率が出る。

**判断の基準**: 誤差が数bps以内なら見積もりは使える(原因は個別の不具合)。
10bps以上なら**見積もりの精度が戦略の前提を満たしていない**ので、プールも
チェーンも投入額も無意味。見積もりの作り方そのものを変える必要がある。

## 価格表の作り直し条件が壊れていた(2026年9月18日に修正)

作り直しの判定に `lastMovePct`(**今回の更新1回ぶんの変化率**)を使っていた。
これは価格表を作ってからの累積のズレではない。

**0.09%ずつ100回動いても一度も閾値を超えず、ズレは無制限に積み上がる。**
再現した結果、sqrtPriceが0.01%ずつ50回動くプールでは:

| | 作り直し | 最終的なズレ |
|---|---|---|
| 旧(1回ぶん) | **0回** | **100bps** |
| 新(累積) | 25回 | 3bps以内 |

100bpsのズレは狙う利幅(5〜50bps)を大きく上回る。送信直前に赤字と確定した
4件の誤差(−3.2 / −5.2 / −8.9 / −13.6bps)が、旧閾値0.1%=10bpsの周辺に
収まっていたことと整合する。**これが幻の利益の正体。**

### 直したこと

- `updateV3FromSwap` が `quoteDriftPct`(表を作った時点からの累積のズレ)を
  計算する。基準は `markQuoteBase` が価格表の作成時に記録する
- 作り直しの判定3箇所すべてを `quoteDriftPct` に切り替えた
- `QUOTE_REBUILD_MOVE_PCT` の既定を 0.1%(10bps)→ 0.03%(3bps)。
  **意味が「1回ぶん」から「累積」に変わっている**点に注意
- 作り直しを**ズレの大きい順**にした。枠が限られているので、
  いちばん誤差が出ているプールから使う

### RPCは増えない

作り直しの本数は `QUOTE_TABLE_PER_TICK`(既定6プール/5秒 = 72プール/分)で
上限が決まっており、閾値を下げても変わらない。変わるのは「限られた枠を
どのプールに使うか」だけ。

### 追いついているかの見方

生存ログの `[価格表の鮮度]` に「基準あり/ズレ超過/最大ズレ」が出る。
**ズレ超過が減らない場合、閾値ではなく作り直しの処理能力が上限**なので、
QUOTE_TABLE_PER_TICK を上げる(RPCは増える)。
V3プール279件を一巡するのに約3.9分かかる計算。

## フォークのプールは環境変数では消えない(2026年9月18日に判明)

`ENABLE_FORK_QUOTER` を空にしても、Polygonの V3 は 191件のままだった。
プール地図は `/data` に保存され起動時に復元されるため、`activeV3Factories`
(発見=追加の制御)では既存のプールを消せない。

取引には使われない(価格表が作れないため)が、**購読枠とRPCを消費し続ける**。
除去には、起動時に `activeV3Factories` に無いファクトリーのプールを
地図から外す処理が要る。**未実施。**

## 【設計】見積もりを「作り置き」から「候補が出てから」へ変える(2026年9月18日)

**これは設計であって、まだ実装していない。** 対象を広げる前に必ずこれを済ませる。

### なぜ今のやり方だと広げられないのか

今は全てのV3プールについて、両方向×8点の価格表を常時作り置きしている。
作り直せるのは `QUOTE_TABLE_PER_TICK`(6プール/5秒 = 72プール/分)までで、
**費用も鮮度もプール数に比例する**。

| V3プール数 | 一巡にかかる時間 |
|---|---|
| 279(現在) | 3.9分 |
| 1,000 | 14分 |
| 5,000 | 69分 |

**69分前の価格で判定すれば、出てくる機会は全部が幻になる。**
プールを3倍にした9月18日に送信直前の6件が6件とも赤字になったのは、
この関係がすでに効き始めていたということ。
つまり**今のやり方のままでは、広げるほど精度が落ちる**。閾値をどう変えても
枠の上限は動かないので、やり方そのものを変えるしかない。

### 変える内容

**「現在価格でふるいにかけて、通ったものだけ正確に見積もる」。**

1段の受取比率は、どんなAMMでも**投入額が増えるほど悪くなる**
(V2の x·y=k も、V3の集中流動性も、出力は投入に対して上に凸)。
したがって**投入額ゼロの極限での比率(現在価格)が、その段で得られる
いちばん良い比率**になる。

経路全体でも同じで、

```
∏(現在価格ᵢ × (1 − 手数料ᵢ)) ≤ 1  ならば、どんな投入額でも黒字にならない
```

これは近似ではなく**必ず成り立つ**。つまり現在価格だけを見たふるいは、
**本物の機会を取りこぼさない**(見逃しゼロ)。通り過ぎるものは出るが、
それは次の段で正確に見積もるので問題にならない。

### この方式の何が良いのか

- **現在価格は作り置きが要らない。** sqrtPriceX96 も準備量も、Swap/Syncを
  受信するたびに更新される。**常に最新で、RPCはゼロ、補間の誤差もゼロ**
- **費用が「プール数」ではなく「候補の数」に比例する。**
  プールが何万件あっても、ふるいを通る本数しか見積もらない
- **今回の幻の正体(累積のズレ)が原理的に消える。** 表を持たないので
  古くならない
- **`V3必須` と `両トークンがV3プールに` の制限を外せる。** V2の段は元から
  正確に計算できており、V3の段もふるいには表が要らなくなるため

### 手順(この順に進める)

1. **まず測る。実装を変える前に、ふるいを通る本数を数えるだけの計測を入れる。**
   RPCはゼロ。通過率が分からないまま切り替えると、候補が毎分数千件出た場合に
   RPCが破裂する。**この測定を飛ばさないこと**
2. 経路の現在価格の積 `cycleEdgeBps(legs)` を計算する(メモリだけ)
3. ふるいを通った経路について、その経路の段だけの価格表を**その場で**作る
   (2段×8点=16件をMulticall3で1回にまとめられる)。作ったら捨てる
4. `legIsUsable` のV3条件を「価格表がある」から「現在価格と流動性がある」へ
5. 作り置きの `refreshQuoteTables` を止める(または上位数十プールの
   温存用にだけ残す)
6. `[判定の精度]` が回復していることを確認してから、制限①②③を外す

### 残る注意点

- ふるいは「**どれかの投入額で黒字になりうるか**」しか答えない。
  ガス代は投入額に依存するので、ガスのハードルは今までどおり
  `findBestAmount` の側で見る
- 通過率が高すぎる場合は、ふるいの閾値を 0bps ではなく
  「ガス代が見合う最小の利幅」まで引き上げて絞る

## 始点トークンの逆算を広げた(2026年9月18日)

### それまで何が起きていたか

始点に使えるかは「桁数と価格が分かるか」だけで決まる。その価格の逆算が
`derivePriceFromStablePools` で、**安定通貨と直結したV2プールしか見ていなかった**。
そのため次の2つが丸ごと価格不明になり、始点から外れていた。

1. **V3にしかないトークン** — Base/Optimismでは活動の97%がV3
2. **安定通貨と直接のプールが無いトークン** — WETH経由などは辿れない

しかも2周まわす作りになっていたが、起点の条件が静的な `stable: true` の
一覧だったため、**2周目で新しく増えるものは1件も無かった**(実質1周)。

### 直した内容(index.js のみ。RPCは1件も増えない)

- **相手が安定通貨でなくてもよい。** その周で価格が確定した通貨なら起点にする
- **V3プールも価格の起点にする。** 現在の価格帯の仮想準備量 (L/√P, L·√P) を
  使う。この2つの比は現在価格そのものになる(USDC/WETHの既知の値で
  両方向とも一致することを確認済み)
- **`PRICE_HOPS`(既定4)回まで隣へ辿る。** 安定通貨 → WETH → その隣、と広がる。
  新しく価格が付かなくなった時点で打ち切る
- **毎回ゼロから作り直す。** 以前は「まだ価格が無いものだけ」を埋めていたため、
  一度付いた価格は二度と更新されなかった。価格は投入額の計算と利益のUSD換算の
  両方に使うので、古いままだとガス代とのハードル比較がその分ずれる

### 安全側の歯止め

価格を間違えると投入額の計算ごと狂うため、**起点にするプールには
`MIN_PRICE_SOURCE_USD`(既定$5,000)の深さの下限を掛けている**。
同じトークンに複数の経路がある場合は、いちばん深いプールを採る。
V3の仮想準備量は価格帯が狭いと深さを多めに見積もるが、その分はこの下限で落とす。

### 効果の見方

生存ログの `始点N` とダッシュボードの「始点に使える通貨」。
**増えた分だけ `[判定の精度]` が落ちていないかを必ず併せて見る。**
落ちた場合は `PRICE_HOPS=1` に下げるか `MIN_PRICE_SOURCE_USD` を上げる。

## ふるいの通過率の計測(2026年9月18日に追加。設計の手順1)

「作り置きをやめる」設計の**手順1**。切り替えると、ふるいを通った回数が
そのまま見積もりの回数(=RPC)になる。**通過率が分からないまま切り替えると
RPCが破裂する**ので、先に数えるだけの計測を入れた。

生存ログの `[ふるい]` 行で見る。

```
[ふるい] 評価12,345 通過[0bps超:230(毎分18) 5bps超:41(毎分3) 10bps超:12(毎分1) 30bps超:0(毎分0)]
         別々の経路87 表ありでの通過64 最良41.2bps
```

- **毎分の通過回数が、切り替え後に必要なRPCの見積もりそのもの。**
  段ごとに出しているので、閾値をどこに置けばRPCがいくつになるかが分かる
- **「表ありでの通過」との差**が、いま価格表が無いせいで**見えていない候補**
- `scanTwoStep` の先頭で、**価格表の有無に関係なく**数える。
  今の判定は価格表のある段しか使えないため、その条件を外さないと
  「切り替えたら候補がいくつ出るか」を測れない

**RPCは1件も増えず、判定の動作にも一切影響しない。**

### ふるいが正しいことの検算(V2の厳密式と総当たりで比較)

| 状況 | ふるい | 総当たりの最良 | 判定 |
|---|---|---|---|
| 価格差なし | −59.91bps | −59.92bps | 通過なし |
| 1%安い側あり | **+39.49bps** | **+39.48bps** | 通過あり |
| 0.6% | −0.27bps | −0.28bps | 通過なし |

いずれも**ふるいの値が総当たりの最良以上**(=上限になっている)で、
**本物の機会を落とした例は無かった**。差が0.01bps程度しかないのは、
現在価格が「投入額ゼロの極限」であり、小さい投入額ではそれにほぼ等しくなるため。

### 最初の計測は計器が壊れていた(2026年9月18日、本番で判明)

入れた直後の実測はこうだった。

```
[ふるい] 評価1,807,536 通過[0bps超:457,738(毎分49,262) …]
         別々の経路5,420 表ありでの通過364,538 最良10,084,520,773,245.5bps
```

**この数字は信用してはいけない。**欠陥が2つあった。

**① 壊れたプールを数えていた。** 最良が **10垓%**。準備量が1weiしかない
プールや死んだトークンの現在価格はいくらでも極端になるので、ふるいは
必ず通る。HANDOVER の「投入$2で利益$24 はハニーポット」と同じ話。
通過の80%が30bps超という、実態としてあり得ない分布になっていた。
→ `SPOT_SCREEN_SANE_MAX_BPS`(既定1000 = 10%)を超える利幅は
**異常として別枠で数え、通過から外す**。

**② 「毎分の通過回数」がRPCの見積もりになっていなかった。**
通過は**評価のたび**に数えていたが、別々の経路は5,420本しかない。
同じ経路を同じ状態のまま何百回も数え直していた。
**同じ状態の同じ経路なら、見積もりは1回で足りる。**
→ 経路ごとに状態の署名を持ち、**変わってから初めて通った回数**
(`fresh`)を数えるようにした。生存ログの「要見積もり」がそれ。

あわせて、**別々の経路を利幅で分けた内訳**も出すようにした。
回数ではなく本数なので実態に近い。

**これは9月18日に自分で挙げた失敗の型そのもの**(「計器の出力を、計器を
検証する前に事実として報告した」)。**新しい計器の最初の数字は、必ず
おかしな値が無いか見てから使うこと。** 今回は `最良` を一緒に出していた
から気づけた。

## 始点が18件から動かなかった本当の原因(2026年9月18日)

価格の逆算を広げても、本番の実測は `始点18` のままだった。**原因は逆算では
なく、その1つ上流の「V3プールの探し方」にあった。**

```js
// index.js  discoverV3PoolsForChain(修正前)
const tokens = Object.keys(getKnownTokens(chain));   // 手書きの4〜7種だけ
```

V2は44,000件のプールを発見しているのに、**V3の探索だけが手書きの一覧に
縛られていた**。さらに絞り込みが「両トークンがV3プールにあるV2だけ残す」
ため、地図に入るトークンがこの一覧に固定される。

実測がそれを裏付けていた。

```
[準備完了] polygon: V2 360件 / V3 187件、桁数0トークン
                                    ↑ 未知のトークンが1件も無い
polygon 7 + arbitrum 6 + avalanche 5 = 18  ← 始点18と完全一致
```

### 直した内容

1. **探索対象を「V2で実際に流動性のあるトークン」まで広げた**(推測しない)。
   深さは**相手側**の価値で測る。相手が手書きの一覧にある通貨なら、
   こちら側の桁数も価格も知らないまま深さが求まる。
   `V3_DISCOVERY_TOKENS`(既定24種)、`MIN_DISCOVERY_DEPTH_USD`(既定$50,000)
2. **ファクトリーへの照会を束ねた**(`findV3PoolsBatch`)。
   `findV3Pool` は1ペア1回のRPCで、24種だと 276ペア×13通り=**3,588回**に
   なる。Multicall3で束ねて**十数回**に収めた。これが無いと広げられない
3. **探索を絞り込みより先に動かした。** 順番が結果を決める。先に絞り込むと、
   これから対象にするトークンのV2プールが判断材料ごと捨てられる
4. **中身が空のV3プールは地図から外す。** 広げると「作られただけで流動性が
   無いプール」も見つかる。残すと購読枠と受信を食うだけ。
   ただし読み取りがまとめて失敗した時に地図を壊さないよう、
   **失敗が半分を超えたら何も外さない**

### 広げたのに0件だった(2026年9月18日、本番で実測)

探索対象を広げた直後の実測は **`[探索対象] polygon: 手書き7種のみ(深さ$50,000
以上の追加候補なし)`** で、**追加候補が0件**だった。

原因は深さの下限ではなく、**保存済みの地図に準備量が入っていなかった**こと。

```js
// loadPoolMap(修正前)
registerPool({ ...e, raw0: 0n, raw1: 0n, ... });   // 準備量を捨てていた
```

準備量を読むのは `prepareChain` で、これは絞り込みの**後**に走る。探索対象を
決める時点では全プールの準備量が0なので、深さがどれも0になり、
誰も下限を超えられなかった。

**直したこと**

1. **地図に準備量を残す**(`snapshotFullMap` / `savePoolMap` / `loadPoolMap`)。
   復元した準備量は古いので `updatedAt: 0` を付け、読み直しの対象にする
2. **探索対象を決める前に、必要な分だけ準備量を読む**(`loadDepthProbeReserves`)。
   対象は**片側が手書きの一覧にある通貨**のプールだけ。物差しが無いプールは
   深さを測れないので読んでも意味がない。上限は `MAX_DEPTH_PROBE_POOLS`(既定15,000)。
   次回以降は保存済みの値が使えるので、ここで読む件数は自然に減っていく

**教訓**: 「広げた」と「広がった」は別物。`[探索対象]` の行を出していたから
0件だと分かった。**効果を測る行を一緒に入れること。**

### 中身が空のV3プールの除外は効いた(同日、実測)

### 効果と費用の見方

- **効果**: 生存ログの `始点N`、`[探索対象]` 行、`[準備完了]` の桁数トークン数
- **費用**: 探索そのものは起動時の十数回だけ。**増えるのは受信**
  (枠の内訳で `受` が大半を占める)。監視プールが増えた分だけ比例するので、
  `枠[…月末見込N%]` を必ず見る。上がりすぎたら `V3_DISCOVERY_TOKENS` を
  下げるか `MIN_DISCOVERY_DEPTH_USD` を上げる
- **精度**: `[判定の精度]` が落ちていないかを併せて見る。落ちたら広げすぎ

## 「ずれが消えた」は早すぎた。原因は手数料(2026年9月19日)

成功1件を見て「見積もりのずれが消えた」と報告したが、**早すぎた**。
件数が増えたあとの実測はこうだった。

```

```

**成功2件(+$0.0109、+$0.0140)に対し、13件がチェーン上では赤字。**
ただし**1円も失っていない**。13件すべて `simulateRoute` が送信前に止めている。
守り(Revert protection)は設計どおり働いた。

### 13件のうち12件が同じDEX

```
[実行] uniswap-v3(0.05%)→dystopia: 赤字(-17.5bps、見込み$0.0138)
[実行] uniswap-v3(0.05%)→dystopia: 赤字(-20.6bps、見込み$0.0182)
[実行] dystopia→uniswap-v3(0.05%): 赤字(-15.9bps、見込み$0.0154)
…
```

**誤差は −11.6 〜 −20.6bps。投入額($9.20〜$16.00)によらずほぼ一定で、
向きにもよらない。**

**幅が一定ということは、深さの計算ではなく手数料の値が違うということ。**
深さの誤差なら投入額とともに広がるし、向きで変わる。
壁0.35%(V3 5bps + V2 30bps)という前提が、実際より**約16bps低かった**。

### なぜ直らなかったのか

`feeProbed`(手数料は実測済み、という印)は**プール地図に保存される**。
一度 true になると二度とやり直されない。生存ログの `手数料0(残0)` が
まさにその状態で、**手数料の実測は1件も走っていなかった**。

### 直したこと

送信直前の確認で**同じプールが2回続けて赤字**になったら、
そのV2プールの `feeProbed` を外す(`REPROBE_AFTER_REJECTIONS`、既定2)。

- 判定はただちに安全側の `UNPROBED_FEE_BPS`(既定45bps)に戻る
- あわせて手数料の実測待ち行列に入り、実際の値が測り直される
- V3は手数料帯が確定しているので対象外

`[手数料の見直し]` 行で、どのプールがいつ外れたかが分かる。

### 教訓

**「精度が直った」を1件で言わない。** `[判定の精度]` は分母が増えてから読む。
成功1件の時点では 1/1 = 100% に見えていた。

## ガス代の見積もりが過大だった(2026年9月19日に修正)

実測すると、事前の見積もりが実際に払った額より一貫して高かった。

| 見積もり | 実際 | 倍率 |
|---|---|---|
| $0.0107 | $0.0074 | 1.45 |
| $0.0125 | $0.0082 | 1.52 |
| $0.0139 | $0.0090 | 1.54 |

**過大な分はそのままハードルの高さになり、本物の機会を赤字と判定する。**
原因は2つあった。

### ① 上限(gasLimit)を費用として数えていた ← 明確な誤り

```js
const gasWithBuffer = (gasUnits * 120n) / 100n;
const measuredGasUsd = await gasUnitsToUsd(chain, gasWithBuffer);  // ← これ
```

`gasWithBuffer` は**送信時の上限**として渡すもので、余裕を持たせるのは正しい。
しかし **EVMは使わなかったガスを請求しない**ので、払うのは `gasUnits` の分だけ。
余裕の20%をそのまま費用に足していた。費用の計算は `gasUnits` に直した。

### ② 単価が実際より高い(残り約27%)

`baseFeePerGas + maxPriorityFeePerGas` は「送信時にこれだけ出す用意がある」
額で、実際にブロックへ入る時の実効単価はそれより低いことが多い。
ガス使用量はほぼ的中している(285,000 対 285,579)ので、ずれているのは単価。

そこで **receipt の実効単価と見積もりの比を覚えて、次から掛ける**。
`[ガス単価の学習]` 行に出る。

**安全のための歯止め**: 比は **0.7〜1.0** に収める。
**見積もりを実際より低くする方向(1.0超)には振らない**し、7割より下げもしない。
ガスが急に上がった場面で過小評価して赤字を出さないため。
件数で重みを付けた平均なので、1件の外れ値で大きく動かない。

## 記録簿の時刻が9時間ずれていた(2026年9月19日に修正)

```js
new Date(e.timestamp).toLocaleString('ja-JP')   // ← 書式だけ日本式、時刻はUTC
```

`toLocaleString` の第1引数は**書式**しか決めない。時刻そのものを日本時間に
するには `timeZone` を渡す必要がある。渡さないとコンテナの設定(UTC)のまま。

**日本式の書式で9時間ずれた時刻が出ていたため、かえって気づきにくかった。**

### 直したこと

- `formatLocalTime()` を追加し、`timeZone: DISPLAY_TIMEZONE`(既定 `Asia/Tokyo`)で整形
- **列の見出しに「日時(日本時間)」と明記**。書式だけでは判別できないため
- 桁を2桁固定にし、年を省いて `09/19 14:16:56` の形に(iPhoneの狭い列で折り返さないように)
- 不正な値や `null` は `-` を返す。タイムゾーンが使えない環境では UTC 表記に落ちる

### 検算

| 記録(UTC) | 画面(日本時間) |
|---|---|
| 09-18 21:42:42 | **09/19 06:42:42**(日付をまたぐ) |
| 09-19 02:30:38 | 09/19 11:30:38 |
| 09-19 05:16:56 | 09/19 14:16:56 |
| 09-19 15:30:00 | **09/20 00:30:00**(日付をまたぐ) |

なお**生存ログなどの標準出力の時刻はRailway側の表示**なので、ここでは変えられない
(Railwayの画面はUTC)。


| | 修正前 | 修正後 |
|---|---|---|
| 見積もり / 実際 | $0.0125 / $0.0082 = **1.52** | $0.0094 / $0.0074 = **1.27** |

**上限(gasLimit)を費用に数えていた分(×1.20)は消えた。**

### 私の見立ては外れていた

残りの27%を「単価が高い」と見ていたが、`[ガス単価の学習]` の
**実際/見積もり=1.000**(=実際の実効単価は見積もり以上)がそれを否定した。
**単価は合っている。残っているのはガス量のずれ。**

`estimateGas` が返す値は、実際に使われる `gasUsed` より多めに出る。

使うか、`estimateGas` と実測の比を同じやり方で学習する。
ただし**事前判定(ハードル)側はすでに実測の平均を使っている**ので、
`粗利プラス → 黒字` の通過率への影響は小さい。優先度は高くない。

## 価格表を保存して起動時に戻す(2026年9月19日)

作り置きをやめてから、**再デプロイのたびに価格表がゼロに戻り、判定が
立ち上がるまで20〜40分かかる**ようになった。この日の計測は何度もその
空白に当たって読めなかったし、その間は取引の機会も取れない。

### 危険なので、条件つきでしか戻さない

古い価格表をそのまま使うのは危険で、**それが9月18日の幻の利益の正体**だった。
そこで**表を作った時の価格も一緒に保存し、起動時に今の価格と比べる**。

- プールが**まったく動いていなければ**、その表はいま作っても同じ → 戻す
- 少しでも動いていれば**捨てる**(作り直しは要求が来た時に走る)
- 基準の価格も**当時の値**で戻すので、ズレの積算がやり直しにならない
  (`setQuoteBase` を追加。`markQuoteBase` は「今の価格」を基準にするので使えない)
- **6時間より古い表は、価格が動いていなくても捨てる**
  (`QUOTE_TABLE_MAX_AGE_HOURS`)。価格が同じでも、流動性の出し入れで
  曲線そのものが変わっているため

保存先はプール地図と同じ場所(`POOL_MAP_FILE` の隣)。`QUOTE_TABLE_FILE` で変えられる。
保存はプール地図と同じ5分ごと。

```
[価格表の復元] 37本を戻しました(0.3時間前の保存) / 価格が動いていて破棄12 / 古すぎ0 / 対象なし3
```

### 確認したこと

| 確かめたこと | 結果 |
|---|---|
| 書き出し→取り込みの往復 | **桁落ちなし**(BigIntを文字列で保存) |
| 動いていない | 復元する |
| 0.2bps / 2bps 動いた | 復元する(閾値3bps以内) |
| **20bps 動いた** | **破棄する** |
| **200bps 動いた** | **破棄する** |
| 基準の価格 | **当時の値のまま戻る** |
| 壊れた値・空の配列 | 弾く |

## 同じチェーンで並行して送る(2026年9月19日)

### 何を直したか

24時間の記録簿で **「送信中」で見送った機会が26件**。成功が40件なので、
見送りは成功の6割に相当する。機会は数分間に集中して来る
(6件が3分間に来た実測がある)ので、「同じチェーンでは一度に1件」の
直列送信だとその山を取りこぼしていた。

直列にしていた理由は nonce の取り合い(2件が同じ番号を取り、片方が
"replacement fee too low" で失われ、粗利$0.4155を丸ごと失った)。

- **ethers の `NonceManager`** で nonce を手元で数える。同時に送っても番号が
  重ならない(同時3件で 7,8,9 と配られることを検証済み)。署名者はチェーン
  ごとに1つを使い回す
- 送信や確定待ちに失敗したら **`reset()`** で鎖上の値に合わせ直す。
  送れなかった番号が手元に残ると、以降の送信が全部詰まるため
- チェーン単位の錠を **プール単位の錠** に変えた。同じプールを使う経路を
  同時に送ると、先に着いた方が価格を動かして後の方が巻き戻り、ガス代だけ
  失うため。**別のプールなら並行して送る**
- 同時に飛ばす本数の上限 `MAX_PARALLEL_SENDS_PER_CHAIN`(既定3)。
  1本が詰まった時の被害を限るため

### 見方

生存ログの `送信中N`(内訳)が減れば効いている。増えていれば
プール単位の錠が効いている(同じプールに集中している)ということ。
`失敗段階[send:…]` が増えたら nonce の問題を疑い、上限を1に戻す
(`MAX_PARALLEL_SENDS_PER_CHAIN=1` で従来と同じ直列になる)。

## 【飛躍の本命】Optimism / Base の再開手順(オーナー立ち会いが必要)

HANDOVERの実測どおり、**手数料の壁が Polygon の35bpsに対し 6bps、ガスも最安**。
$5投入時のハードルは Polygon 59bps に対し **Optimism 16bps**。
同じ価格差の分布なら、**届く経路が数倍**になる。

止めていた理由は「未監視ファクトリーの価格表が作れない」ことだったが、
自前の `quoteV3`(フォーク対応)と Algebra 対応で**解消済み**。
残っているのは**チェーンごとの準備**だけ。

### 手順(1チェーンずつ。Optimism → Base の順)

1. **RPC を用意**: Chainstack で Optimism のノードを追加し、
   `OPTIMISM_RPC_URL` と `OPTIMISM_WSS_URL` を Railway に設定
   (URLは秘密情報。リポジトリには絶対に書かない)
2. **コントラクトをデプロイ**: `RUN_MAINNET_DEPLOY=optimism` で起動。
   ログに出た住所を `MAINNET_CONTRACT_ADDRESS_OPTIMISM` に設定し、
   `RUN_MAINNET_DEPLOY=false` に戻す。デプロイ用のガス(ETH)が
   bot ウォレットに要る(Optimism は数十セント)
3. **稼働に加える**: `ACTIVE_CHAINS=polygon,arbitrum,avalanche,optimism`
4. **フォークを有効化**: `ENABLE_FORK_QUOTER=polygon,optimism`
5. **確認**: `[発見] optimism univ3-fork-d(uniswap): V3プール○件` が0件で
   ないこと、`[準備完了] optimism` の監視プール数、`[判定の精度]`

**注意(点検で判明)**: V3プールは起動ごとに探索されるが、**V2プールは
プール地図の再構築時にしか集めない**(保存済みの地図があると週1回)。
新しいチェーンを加えた直後は Optimism の V2 が地図に無いため、始点の拡張
(深さで選ぶ)も V2↔V3 の経路も、まず手書きの5トークン分だけになる。
初回だけ `MAP_REBUILD_AFTER_HOURS=0` で起動して地図を作り直し、終わったら
`168` に戻す(再構築は全チェーンぶんで数百回のRPCを使う。枠には十分収まる)。

Arbitrum / Avalanche の**再デプロイ**も同じ手順(手順2だけ)。
これで両チェーンのフォークのプールと、段ごとの答え合わせが使えるようになる。

失敗5件: Arbitrum 2段(送信前に状況変化)、Arbitrum 2段 $276(巻き戻り)、
**Polygon 3段(制限時間超過)**、Avalanche 3段 ×2(巻き戻り)。
巻き戻りは送信から確定までの数秒で状態が動いたもの(競争または遅延)で、

### 見つけた自分のバグ: 制限時間超過で nonce を合わせ直していなかった

並行送信(NonceManager)は send / wait の失敗で `reset()` するが、
**20秒の制限時間超過は index.js の Promise.race で起きるためそこを通らない**。
手元の nonce が1つ進んだまま残り、その送信が未確定のまま消えると、
以降の送信が全部その番号待ちで詰まる。旧コードは送信のたびに nonce を
読み直していたので自然に直っていた。
→ `resetNonce` を公開し、index.js の失敗処理(制限時間超過を含む)からも呼ぶ。

## Optimism の費用に L1 データ手数料を入れた(2026年9月20日)

OP Stack(Optimism / Base)は、L2 の実行費(gasUsed × 単価)とは別に、取引の
データを L1 に書く費用を取引ごとに取る。receipt の `l1Fee` に出るが、ethers の
`receipt.gasUsed × receipt.gasPrice` には入らない。bot はこれを数えておらず、
Optimism の費用を実態より低く見積もっていた(L2 の実行費は極小なので、L1 側が
費用の大半になり得る)。Arbitrum は L1 分を gasUsed に折り込む方式なので影響しない。

- 事前判定: 代表的な2段の取引(418バイト)で予備コントラクト GasPriceOracle
  (`0x4200…000F`)の `getL1Fee` に聞いた値を5分だけ覚えて足す。確定した取引の
  `l1Fee` が貯まればその平均を使う(`getTypicalL1FeeWei`)
- 送信直前: 実際の呼び出しデータで作った取引(署名は仮)で聞いて足す(`estimateL1FeeWei`)
- 確定後: 生の receipt から `l1Fee` を読んで費用に足し、`[実行] 確定:` の行に
  「うちL1データ$…」と出す。記録簿には `actualL1FeeUsd` を残す
- OP Stack 以外のチェーンでは全て 0 で、動きは変わらない(鎖に触れない試験で確認)

Optimism の `[惜しい]` が粗利プラス40/112本あるのに黒字が出ない理由の一つが、
費用の過小評価「ではなく」本当にガス代に届いていないのかは、この修正後の
`[生存]` の 内訳[下限] と `[実行] 確定:` の L1 の実額で判断する。

## Optimism で確定前(pending)の状態を使う: Flashblocks(2026年9月20日)

### 背景: 「1ブロック遅い」
bot は WebSocket の logs 購読で動くが、これはブロック確定(Optimism は2秒)まで
届かない。専業の裁定者は確定前の状態で動くので、常に1ブロック遅かった。
OP Stack の Flashblocks は、シーケンサーが 200〜250ms ごとに確定前の部分ブロックを
配る仕組み。Optimism は先着順なので、確定前に検知できれば同じブロックの後ろに
自分の取引が入る。

### 調べたこと(2026年9月20日)
- Polygon は 2026年4月からプライベートメンプールと VeBloP に移行し、未確定取引を
  見る前提が崩れている。FastLane/Atlas のバックラン入札は、未確定取引の配信を
  自前で用意する必要があり(Chainstack は通知1件=1リクエストで枠が数日で尽きる)、
  保証金と 250ms の封印入札で専業5〜8社と競う。安くは直せないので保留
- Arbitrum は Timeboost(優先レーンの入札)が3社で99.7%を独占。シーケンサー配信
  (無料)は数百ms早いだけ。後回し
- Optimism は Chainstack の既存端点が Flashblocks 対応済み。ただし WSS の購読
  (`newFlashblocks` / `newFlashblockTransactions`)は「Invalid params」で拒否され、
  **標準 RPC の pending タグ**として見える形だった(起動時の確認ログ):
  ```
  [Flashblocks/pending] optimism: latest 157148294(29件) / pending 157148295(17件) → … pending 157148295(31件)
    / pendingがlatestより先 5/5回 / 同じpendingの中で取引数が増えた: はい
  [Flashblocks/pending] optimism: eth_getLogs(pending) 72件(ブロック 157148296) / eth_call(pending) 通った
  [Flashblocks] optimism: Flashblocks の購読は拒否(標準の pending タグで読む)。比較用 newHeads の間隔 1899/1998/2125/1911/1949ms
  ```
- Optimism の L1 データ手数料は約$0.000003/件で無視できる(費用に入れる仕組みは入れた)

### 実装(2026年9月20日)
- `dex-onchain-realtime.js`: `FLASHBLOCKS_PENDING_CHAINS`(既定 optimism)のチェーンで、
  監視対象のプールの `eth_getLogs(fromBlock/toBlock = pending)` を `FLASHBLOCKS_POLL_MS`
  (既定 400ms)ごとに取り、確定を待たずに判定へ回す。同じイベントは txHash と logIndex
  で覚え、pending で何度届いても、確定後に logs 購読で届いても、2回目以降は判定に
  回さない。確定後に届いた時に「先読みできた時間」を記録し、`[生存]` の
  `先読み[optimism:事前N件 確定で照合N件 先行平均Nms …]` に出す
- 読み取りも pending に揃える: 準備量と V3 状態と価格表(Multicall3 の `aggregate3`)、
  公式 Quoter、送信直前の `simulateRoute`(eth_call)、ガス見積もり(`eth_estimateGas` を
  pending を明示して生で呼ぶ。ethers の estimateGas はブロックの指定を送らない)。
  他のチェーンは latest のままで動きは変わらない(`readBlockTag`)
- RPC の消費: 400ms 間隔で1日約216,000、月約650万(枠2,000万の3割)。効果を見て
  `FLASHBLOCKS_POLL_MS` を調整する(250ms なら月約1,040万)
- 危険: 確定前の状態は稀に確定しない(取引が落ちる)ことがある。その場合、
  送信した取引が巻き戻ってガス代だけ失う(Optimism のガスは$0.005前後)

### 確かめること
- `[生存]` の 先読み の「先行平均」が数百ms〜1秒台になっているか(確定より早く見えているか)
- Optimism の `[機会]` と送信が増えるか、送信直前の赤字(価格表のずれ)が減るか
- 枠の月末見込が 50% を超えないか

3,300件が全件一致)。**速さは足りていて、足りないのは見ている範囲**だった。

### 何が足りなかったか

| | 実測 |
|---|---|
| 監視ペア | **9ペア**(手書きの5通貨の組み合わせだけ) |
| 監視プール | 57(Uniswap 30 + fork-d 27)。**Velodrome が1つも無い** |
| 最小の壁 | 35bps(0.05%+0.30% の組が中心) |
| 5時間の黒字判定 | **0件**。経路194本の最良でも壁を超えず |

### 対策: scripts/pool-scout.js

ファクトリーの住所を当てにせず、**実際に取引が起きているプール**を
Swap / Sync イベントから拾う(アドレス指定なしの eth_getLogs)。

- 正体は `factory / token0 / token1 / fee / tickSpacing / liquidity / getReserves` を
  Multicall3 で一括して読む。`fee()` が無いCLプール(Ramses系・Slipstream系)は
  **tickSpacing から手数料を見積もる**(1→1bps / 10,50→5bps / 60,100→30bps / それ以上→100bps)。
  これは推測なので**低めに倒す**。判定の真偽は価格表(自前の quoteV3)が決めるため、
  ずれても「ふるいを通る/通らない」が変わるだけで嘘の利益にはならない
- 見積もりは自前の quoteV3(プール住所を直接渡す)、コールバックは名前不問の
  fallback。**コントラクトの変更は不要**
- 住所の分からないファクトリーは自前の見積もりが要るので、
  `ENABLE_FORK_QUOTER` が無効なチェーンでは載せない

### 増やしすぎない(RPCの枠を守るため)

プールを増やすと WebSocket の受信がそのまま RPC の消費になる(1件=1リクエスト)。
Optimism は57プールで1日約9万件。無制限に足すと枠2,000万を超えるので、
**今の監視ペアを深くするものだけ**載せる:

| 条件 | 扱い |
|---|---|
| 両方のトークンが手書きの一覧にある | 載せる(同じペアに安い手数料のプールが増え、**壁が下がる**) |
| 片方が一覧にあり、そのペアが既に地図にある | 載せる(比べる相手が増える) |
| それ以外(新しいペア) | **載せず、件数と上位だけ報告**。判断してから足す |

1回の追加は `SCOUT_MAX_NEW_POOLS`(既定150)まで。RPC は1回の調査で
`SCOUT_MAX_REQUESTS`(既定40)まで。起動時と6時間ごとに実行する。

環境変数: `SCOUT_CHAINS`(既定 optimism)/ `SCOUT_BLOCKS`(3000)/
`SCOUT_MAX_NEW_POOLS`(150)/ `SCOUT_MAX_REQUESTS`(40)/ `SCOUT_INTERVAL_HOURS`(6)

### 確かめること

- `[プール発見] optimism: …ブロックで○プールが稼働。○件を調べ、**○件**を地図に追加`
  が0件でないこと(0件なら Swap の識別子か読み取りを疑う)
- `[準備完了] optimism` のプール数と、`[惜しい] optimism` の**最小の壁**が下がるか
- `[生存]` の `受信[optimism:N]` と `枠[… 月末見込N%]`。**30%を超えたら**
  `SCOUT_MAX_NEW_POOLS` を下げる
- `[プール発見] … 未採用で取引の多いペア上位:` に出る通貨。ここが次に広げる候補
