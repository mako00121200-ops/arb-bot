# Aave V3 小口清算の設計(2026年9月21日)

裁定(いまの戦略)とは別の収益源として、Aave V3 の清算を足す計画。
**元手ゼロ**で、**1回$5〜50**を狙う。$50/日に必要な回数は **1〜10回**。

この文書は設計だけ。実装と再デプロイはオーナーの了承を得てから行う。

---

## 1. なぜこれをやるのか

| | いまの裁定 | Aave 清算 |
|---|---|---|
| 1回の利益 | $0.005〜0.024 | **$5〜50** |
| $50/日に必要な回数 | 2,000〜10,000 | **1〜10** |
| 元手 | 不要(フラッシュスワップ) | **不要**(同じ仕組みが使える) |
| 競争 | 浅い帯は競合ゼロ(実測) | 大口は激戦、**小口は放置** |
| 出方 | 市況次第で毎時 | **荒れた日に集中** |

根拠(2026年9月21日のリサーチ):

- 清算の46%を上位5者が握る(Gini 0.83)。ただしこれは**大口**の話
- Aave 自身が V4 で **$1,000未満を「ダスト」** として扱いを変えている。
  = 小口が放置されている証拠
- 2026年1月31日〜2月5日の急落では **5日で12,500件・$4.29億**。
  静かな日は0件、荒れた日に集中する「保険の売り手」型の収益

## 2. 仕様(一次情報で確認済み)

### 清算の関数
```solidity
function liquidationCall(
    address collateralAsset, // 受け取る担保
    address debtAsset,       // 肩代わりする借金
    address user,            // 清算される人
    uint256 debtToCover,     // 肩代わりする額
    bool    receiveAToken    // false = 担保そのものを受け取る
) external;
```

- `debtToCover` に `type(uint256).max` を渡すと、**その時の上限まで自動で**清算する
- `receiveAToken = false` にして**担保そのもの**を受け取る(すぐ売るため)

### 清算できる条件と量
| 健全度(HF) | 一度に返せる割合 |
|---|---|
| HF ≥ 1 | **清算できない** |
| 0.95 ≤ HF < 1 | 借金の **50%** まで(DEFAULT_LIQUIDATION_CLOSE_FACTOR) |
| HF < 0.95 | 借金の **100%** まで(MAX_LIQUIDATION_CLOSE_FACTOR) |

### 健全度の読み方
```solidity
function getUserAccountData(address user) external view returns (
    uint256 totalCollateralBase,        // 担保の合計(オラクルの基準通貨、USDなら8桁)
    uint256 totalDebtBase,              // 借金の合計(同上)
    uint256 availableBorrowsBase,
    uint256 currentLiquidationThreshold,// bps(8500 = 85%)
    uint256 ltv,                        // bps
    uint256 healthFactor                // **18桁**。1e18 = ちょうど1.0
);
```
**`healthFactor < 1e18` で清算できる。**

### 利益の出どころ
担保を **5〜10%引き**で受け取れる(資産ごとの liquidationBonus)。

```
受け取る担保 = debtToCover × 借金の価格 × (1 + ボーナス) / 担保の価格
```

$500 の借金を肩代わりしてボーナス5%なら、**$525 相当の担保**を受け取る。
差額 $25 から、担保を売る時の手数料とガス代を引いたものが利益。

## 3. 設計:いまのコントラクトをほぼそのまま使える

いまの `executeRoute` の流れは次の形になっている。

```
1段目のプールから「先に受け取る」(フラッシュスワップ)
  → 2段目以降をスワップ
  → 1段目に返す
```

清算はこう置き換わるだけ。

```
1段目のプールから debtAsset を「先に受け取る」
  → ★ liquidationCall で借金を肩代わりし、担保を5〜10%引きで受け取る ★
  → 担保を売って、返す通貨に戻す
  → 1段目に返す
```

**★の1手が増えるだけ**で、フラッシュスワップ・コールバック・返済・利益判定は
すべて既存のものが使える。

### コントラクトへの追加(最小)

```solidity
struct Liq {
    address pool;            // Aave V3 Pool
    address collateralAsset; // 受け取る担保
    address debtAsset;       // 肩代わりする借金
    address user;            // 清算される人
    uint256 debtToCover;
}

/// 清算して、担保を売って、フラッシュスワップを返す。
/// legs[0] で debtAsset を受け取り、legs[1..] で担保を asset に戻す。
function liquidateRoute(
    address asset, uint256 amount, Leg[] calldata legs,
    uint256 minProfit, Liq calldata liq
) external onlyOwner;

/// eth_call 用。結果を SimulationResult で返して取り消す(既存と同じ作り)。
function simulateLiquidate(
    address asset, uint256 amount, Leg[] calldata legs, Liq calldata liq
) external onlyOwner;
```

内部は `_runRouteAndRepay` に**清算の1手**を差し込むだけ:

```
1段目で受け取った debtAsset の量を running とする
  ↓
liq.pool が指定されていれば:
    debtAsset を liq.pool に approve(必要な分だけ)
    liquidationCall(collateral, debt, user, running, false)
    approve を 0 に戻す
    running = 受け取った担保の量(残高の差分で測る)
    tokenIn = collateralAsset
  ↓
legs[1..] を今までどおりスワップ
  ↓
返済・利益判定は既存のまま
```

**安全性について。** `liq.pool` を引数で受け取るのは、偽の住所を渡されると
危険に見える。しかし `liquidateRoute` は `onlyOwner` で、呼べるのは bot の
ウォレットだけ。チェーンごとに住所を埋め込むより、**bot 側で管理して
実測で確かめる**方が、チェーンを増やす時に再デプロイが要らない。

**承認(approve)は使う分だけ出して、直後に0へ戻す。** 残したままにしない。

### bot 側(新しいファイル)

```
scripts/aave-liquidation.js
  ├ 借り手の名簿を作る    … Pool の Borrow イベントから onBehalfOf を集める
  ├ 健全度を測る          … Multicall3 で getUserAccountData をまとめて読む
  ├ 危ない人を絞る        … HF < ALERT_HF(既定1.05)を「見張り名簿」に
  ├ 清算できる人を見つける … HF < 1.0
  ├ どの担保・どの借金か決める … いちばん大きい組み合わせ
  └ 利益を見積もる        … ボーナス − 担保を売る手数料 − ガス代
```

**既存の仕組みをそのまま使うところ:**
- Multicall3(`scripts/multicall-reserves.js`)
- ガス代の計算(`scripts/gas-cost.js`、ガス単価の補正比も効く)
- 担保を売る経路の計算(`scripts/opportunity-scanner.js` の `legAmountOut`)
- 送信前の確認(`simulateLiquidate` → 既存の `simulate` と同じ形)
- 通知(`scripts/owner-alert.js`)

## 4. RPC の枠(いちばんの制約)

いまの使用量は **6.4%・月末見込23%**(枠2,000万)。清算を足すといくら増えるか。

| 処理 | 頻度 | 1回の呼び出し | 月間(1チェーン) |
|---|---|---|---|
| 借り手の名簿の更新 | 10分に1回 | 1(getLogs) | 4,320 |
| 全員の健全度 | 10分に1回 | 借り手2,000人 ÷ 150 ≈ **14** | 60,480 |
| 見張り名簿の健全度 | 1分に1回 | 危ない人50人 ÷ 150 ≈ **1** | 43,200 |
| 清算の詳細と確認 | 清算が出た時だけ | 3〜5 | ごく少数 |
| **合計** | | | **約11万/チェーン** |

**5チェーンで約55万。枠の2.8%。** 今の23%に足して**約26%**。十分収まる。

ただし借り手の人数はチェーンによって桁が違う可能性がある。
**まず1チェーン(実測で借り手が最も少ないところ)で測ってから広げる。**

## 5. 正直なリスクと弱点

| リスク | 中身 | 対策 |
|---|---|---|
| **空振り** | HF<1 を見つけても、先に誰かが清算する | 送信前の確認(`simulateLiquidate`)で弾く。ガス代は失わない |
| **担保が売れない** | 受け取った担保を売る深さが無いと、返済できずに取り消し | 経路を先に計算し、売れる量だけ `debtToCover` に指定する |
| **0件の日が続く** | 静かな相場では1件も出ない | 裁定は止めない。**両方を並行して動かす** |
| **人数が多すぎる** | 借り手が数万人だと健全度の巡回が枠を食う | 段階的に。1チェーンで測ってから広げる |
| **オラクルの更新待ち** | HF は価格更新で動く。更新の瞬間が勝負 | 第1段では追わない。第2段で Chainlink の更新を起点にする |
| **再デプロイが必要** | コントラクトを変える | オーナーの立ち会い。5チェーン分 |

**いちばん正直に言うべきこと:** 小口が本当に放置されているかは、
**うちがまだ実測していない**。外部の研究と Aave 自身の扱いからそう推定しているだけ。
だから**第1段は「測るだけ」**にする。

## 6. 進め方(段階を分ける)

### 第1段:測るだけ(再デプロイ不要・リスクゼロ)— **2026年9月21日に実装済み**
`scripts/aave-liquidation.js` で、**読み取りだけ**を行う。

- 借り手の名簿を作る(チェーンごとの人数が分かる)
- 健全度を測り、`HF < 1.05` が何人いるかを記録
- `HF < 1.0`(清算できる)が出たら、**その規模と利益の見積もりをログに出す**
- **送信は一切しない**

**これで次が分かる:**
1. 1日に何件、清算できる機会があるか
2. その規模はいくらか($100未満か、$1,000超か)
3. どれくらいの速さで他人に取られるか(次の巡回で消えていれば取られた)
4. RPC をいくら食うか

**1〜3日ぶん貯めてから、第2段に進むか決める。** 見合わなければここで止める。

### 第2段:コントラクトの追加(再デプロイが必要)
第1段の実測で「やる価値がある」と判断できた場合のみ。

- `liquidateRoute` と `simulateLiquidate` を追加
- ローカルの EVM(anvil)で、Aave をフォークして試験する
- **5チェーン分の再デプロイ**(オーナーの立ち会い)

### 第3段:速さ
第2段で実際に取れてから。

- Chainlink の価格更新を起点にする(HF が動く瞬間に反応する)
- Flashblocks の先読みを清算にも使う(Base / Optimism)

## 8. 第1段の実装で決めたこと(2026年9月21日)

### 名簿の作り方:前へ追いつきながら、後ろへも伸ばす
Aave Pool は何年も前からあるので、過去のログを一度に全部は遡れない。
毎回の巡回で「新しく借りた人を拾う(前へ)」と「昔から借りている人を拾う(後ろへ)」を
**両方少しずつ**進める。

**この作りの弱点を承知しておく。** 始めた直後は「直近の借り手」しか名簿に無いので、
**測れる件数は本来より少なめに出る**。日が経つほど名簿が完成に近づく。
第1段の結論を出す時は、名簿がどこまで遡れたか(ログに出る)を一緒に見ること。

### RPC の上限を全部の入口に付けた
枠を食い潰すと裁定の方が止まり、本末転倒になる。

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `AAVE_CHAINS` | `base,optimism` | 対象チェーン。**まず2つで始める** |
| `AAVE_ENABLED` | `true` | `false` で完全に止まる |
| `AAVE_MAX_LOG_REQUESTS` | 6 | 1巡回の getLogs の上限 |
| `AAVE_LOG_CHUNK_BLOCKS` | 2000 | getLogs 1回のブロック数 |
| `AAVE_MAX_ROSTER` | 5000 | 名簿の人数の上限 |
| `AAVE_USERS_PER_CALL` | 150 | 束ね1回で読む人数 |
| `AAVE_MAX_SWEEP_CALLS` | 40 | 全員を測る時の束ねの上限 |
| `AAVE_SWEEP_INTERVAL_MS` | 10分 | 名簿の更新と全員の測定 |
| `AAVE_WATCH_INTERVAL_MS` | 60秒 | 危ない人だけの測り直し |
| `AAVE_WATCH_HF` | 1.05 | これ未満を「危ない」とする |

### 住所は思い込みで使わない
Pool の住所は公開情報だが、**起動時に `getUserAccountData` が実際に返るかを
確かめてから**見張る。返らないチェーンは自動で外し、ログに残す。

```
[清算] base: Aave V3 Pool 0xA238Dd80… に応答を確認しました
[清算] optimism: Aave V3 Pool 0x794a6135… が応答しません(…)。このチェーンは見張りません
```

### 見積もりは控えめに
担保のボーナスは資産ごとに5〜10%あるが、第1段は**一律5%**で見積もる。
実際の値を読むには reserve ごとの設定が要り、RPC が増えるため。
**第1段の粗利は「少なくともこれくらい」という下限**として読むこと。
担保の売却手数料とガス代もまだ引いていない。
