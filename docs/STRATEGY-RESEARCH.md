## 2. 依頼文の設計への技術的な訂正(2点)

### 訂正1:Backrun に「Post-Swap Pool State Simulation」は**要らない**

依頼の流れは `大口Swap検知 → Swap後の価格を事前Simulation`。
だが **V3 の `Swap` イベントは更新後の `sqrtPriceX96` と `liquidity` を、
V2 の `Sync` は更新後の準備量を、そのまま載せている。**
**シミュレーションではなく、真の値が届く。**

事前シミュレーションが要るのは「mempool の**未実行**トランザクションを先回りする」場合だけ。
我々が読んでいるのは Flashblocks の**実行済み・未確定**ログなので、**後状態は確定している**。

→ **#4 で作るべきは、後状態の推測ではなく「規模の判定」と「段分け」だけ。**

### 訂正2:Backrun の競争は「速さ」ではなく**順序**で決まるチェーンがある

- **base / optimism(Flashblocks)** … TEE シーケンサが**優先手数料で並べ替える**。速さ+入札。我々は先読み1.46秒を持つ
- **arbitrum(Timeboost)** … 60秒の**封印入札(2位価格)**で即時レーンを1者が落札。**非落札者は既定で200ms遅延**。
  **優先手数料では順番が1つも変わらない。** ここでの Backrun は構造的に不利(§8-1で決着済み)
- **avalanche / polygon** … 素の優先手数料順

→ **#4 の Shadow は base / optimism / avalanche / polygon に限る。arbitrum に労力を割かない。**

## 3. 各戦術の詳細

### 【1】Oracle Update Arbitrage

**仕組み** Chainlink `AnswerUpdated` を受信 → `feedToAssets` で影響資産 → **`byToken` でその資産を含むプール** → そのプールを起点に `scanForChangedPool`。
Oracle 自体と取引するのではなく、「Oracle が動いた = その資産の板が動く」ことを**他者より先に知る**。

**再利用** 購読・フィード解決・資産対応表(liquidation-monitor)、トークン索引・経路探索・投入額最適化・ガス・シミュレーション(既存全部)。
**欠けているもの** 資産→プールの join(既存2部品を繋ぐだけ)/ 段分け / Shadow 記録。
**必要な設備** なし(購読は既に張ってある)。
**必要な元手** ゼロ(フラッシュスワップ)。
**RPC** ほぼ増えない。再計算は手元の地図で行う。
**遅延要件** 中。Oracle 更新は1分〜1時間に1回で、**全員が同じイベントを見る**。勝負は更新→送信の時間。
**競争** 高い(専業が同じ購読をしている)。ただし **Aave 清算との合わせ技は別**(§下)。
**主な危険** 地図が古いまま「動いたはず」と誤判定する。→ 既存の `simulateRoute` が最後に弾く。
**Shadow 設計** 価格更新ごとに、影響プールの再計算結果(純利・段)を記録。**送信しない。**
**工数** 小(半日)。**本番への道** Shadow で $0.5+ が1日N件出るか → 出れば既存の `handleOpportunity` に流すだけ。

**清算との合わせ技は既に動いている。** `Oracle更新 → HF変化 → 清算候補` は base で稼働中
(21:22 時点 `価格更新6(即47) 候補2`)。ただし**捕まえた2件は借金$0.02のダスト**。
95日の実測で **92%が$100未満**、$1,000超は **1.06回/日**。狙いはその 1.06回/日。

### 【2】Stablecoin / LST / LRT Peg Arbitrage

**仕組み** 「理論価値 vs 市場価格」。**オンチェーンで基準価値を計算できるものだけ**を対象にする。

| 資産 | 基準価値の取り方 | 償還の制約 |
|---|---|---|
| wstETH | `stEthPerToken()` | wstETH↔stETH は即時。stETH→ETH は**出金待ち行列** |
| ERC-4626 Vault | `convertToAssets(1e18)` | Vault ごと。即時のものと待ち行列のものがある |
| cbETH / rETH など | 各々の rate 関数 | 多くは**即時償還不可** |
| USDC / USDT / DAI | **理論値は $1 だが、償還は KYC が要る口座経由** | **我々には使えない** |

**ここが肝心。** ステーブルのペグ乖離は「理論値」があっても**償還できない**ので、
結局「DEX A vs DEX B」に戻る = 既存戦術と同じで、追加価値は薄い。
**価値があるのは、オンチェーンで即時に交換レートが確定し、かつ交換が atomic に行える資産だけ**
(wstETH↔stETH、ERC-4626 の一部)。

**再利用** 価格表・経路探索・投入額最適化・ガス・シミュレーションは全部そのまま。
**欠けているもの** 資産ごとの rate 読み取り(ABI と住所)/ 乖離の監視 / 償還制約の表 / 段分け。
**必要な設備** なし。**必要な元手** atomic に閉じるならゼロ。**閉じないなら在庫が要る**(オーナー判断)。
**RPC** rate の読み取りが資産×頻度ぶん増える(数十件/分。枠は60%空き)。
**遅延要件** 低い。デペグは秒ではなく分〜時間の単位で動く。**ここが最大の長所。**
**競争** 中。ただし**遅延要件が低い = 設備で負けない**ので、我々の条件に合う。
**主な危険** 「理論値」を信じて**償還できない資産**を掴む。→ 償還制約の表を先に作り、
atomic に閉じられないものは**測るだけ**にする。
**Shadow 設計** 対象資産の rate と各DEX価格を定期取得し、乖離・実行可能量・純利を記録。
**工数** 中(1〜2日)。**本番への道** 乖離が実際にガス代を超える資産が見つかってから。

### 【3】Uniswap v4 Arbitrage

**仕組み** v4 は全プールが単一の `PoolManager` に入り、プールは `PoolKey`(通貨2つ・手数料・tickSpacing・**hook住所**)で識別される。
hook が `beforeSwap`/`afterSwap` で**手数料や交換結果そのものを変えられる**ため、
**表面の価格差では利益を判定できない。**

**再利用** ほぼ無い。イベント購読の骨組み・ガス・記録・段分けだけ。
**価格計算は作り直し**(v4 の `Swap` イベントは別形式、状態は `PoolManager` の `extsload` で読む)。
**欠けているもの** プール発見(`Initialize` イベント)/ hook の分類 / v4 の quote / Flash Accounting 前提の実行。
**必要な設備** なし。**必要な元手** ゼロ(ただし実行は v4 用に作り直し)。
**RPC** 新規購読ぶん増える。**遅延要件** 他と同じ。
**競争** 未知。v4 は新しく、**hook ごとに性質が違うので総取りしにくい**可能性はある。
**主な危険** **hook が悪意を持てる**(afterSwap で取り上げる等)。
→ **hook 住所ごとの白名簿制**にし、素性の分かる hook 以外は触らない。
**Shadow 設計** 依頼文の Observer をそのまま:発見→hook分類→Swap監視→後価格→他DEX比較→
**hook と手数料を入れた**期待純利。**hook 住所ごとに集計**する(ここが要点)。
**工数 大(3〜5日)。** **本番への道** Shadow で「利益が出る hook」が特定できてから、その hook 限定で実行。

### 【4】Backrun Arbitrage ← **最も安く、最も早い**

**仕組み** 大口スワップがプール価格を動かした直後に、他DEXとの差を取る。
**我々は既にこれを(規模を問わず)やっている。** 欠けているのは
「**大口だったか**」の判定と、大口に絞った時の成績の測定。

**再利用 約90%。** 購読・先読み(base 1.46秒)・後状態(イベントが運ぶ)・
経路探索・投入額最適化・シミュレーション・ガス・競合判定、全部ある。
**`lastMovePct` という「動いた大きさ」も既に計算済み**(ただし誰も読んでいない)。
**欠けているもの**
1. `movePct` を `handleOpportunity` で**読む**(現在 `meta` に入れて捨てている)
2. 6段の利益分け
3. Shadow の記録(規模帯 × 純利)

**必要な設備** なし。**必要な元手** ゼロ。**RPC** 増えない(手元の値で判定)。
**遅延要件 高い。** ただし base / optimism では **先読み1.0〜1.5秒**を既に持っている。
**競争** 最も激しい。だが**我々の負け方は「見えていない」ではなく「送って負ける」**
(`先越され` として計上済み)ので、改善余地が測れる。
**主な危険** 大口に絞ると件数が減り、標本が集まらない。→ 段分けで全件を記録し、後から絞る。
**工数 最小(数時間)。** **本番への道** `movePct` を読んで段別の成績を見る → 大口帯の勝率が高ければ、
その帯だけ優先手数料を上げる(`priorityShareFor` が既にある)。

**新しい基盤を作らない。** 既存の `reactToPoolChange` が既にそのバスになっている。
足すのは**入口(トリガー)**と**出口(記録)**だけ。

```
[既存] V2 Sync / V3 Swap / Algebra Swap  ──┐
[既存] Flashblocks 先読み(base/optimism) ─┤
[既存] Chainlink AnswerUpdated ───────────┤→ 影響資産 → byToken → 影響プール
[新規] LST/Vault の rate 更新 ─────────────┤        ↓
```

**Shadow は `handleOpportunity` の手前に置く。** 既存の送信判断には一切触らない。

依頼の記録項目はすべて既存の値から取れる。**取れないものは空欄にし、推測で埋めない:**

## 10. 「経路なし」の組を地図に足す(2026年9月22日 23:40 JST、**オーナーの指示**)

### 何が起きていたか

UniswapX の計測、base の漏斗:

```
見133
 ├ 古すぎ 51        … 約定から180秒超(値動きが混ざる)
 ├ 約定時刻なし 1
 └ 新しい 81
     ├ **経路なし 68(84%)**  ← ここで落ちていた
     └ 値付け 13
         └ 模型が勝ち 7 → チェーンで確認 7勝/0敗 $10.5640
```

**$10.56 は、UniswapX で起きていることの16%を見た数字でしかなかった。**

他チェーンも同じ:arbitrum 85%、polygon は**50件全部が「約定時刻なし」で1件も使えていない**。

### 直し方:総当たりではなく「足りないと分かっている組だけ」

`pool-scout.js`(取引のある全プールを見て上位を採る)とは**逆向き**。
足りない組が分かっているので、**その組だけ**をファクトリーに聞く。はるかに安い。

1. `uniswapx-probe.js` … 経路なしで落ちた組を **`missing` に控える**(件数と注文額の両方)
2. `pair-filler.js`(新規)… 控えを**注文額の大きい順**に並べ、
   そのチェーンの V3 ファクトリー全部に `getPool(tokenA, tokenB, 手数料帯)` を聞く
3. 見つかったものを `registerPool({source:"scout", updatedAt:0})` で登録
   → 準備量・桁数・V3の状態は**既存の定期処理**が読む

**並べ方は件数ではなく注文額。** 1件$1が100件ある組より、1件$5,000が3回ある組の方が効く
(実際、最良の勝ちは **$1,901 の注文**だった)。

### 歯止め

| | |
|---|---|
| 1回に扱う組 | 3組(`PAIR_FILL_MAX_PER_RUN`) |
| 足切り | 注文額 $100未満の組は足さない |
| 再訪 | **一度調べた組は、見つからなくても二度と聞かない**(無駄な問い合わせの防止) |
| 枠 | 月末見込70%超で停止(`pool-scout` と同じ判定。`getLastRpcUsage`) |
| ゴミの掃除 | `source:"scout"` なので**24時間イベントが無ければ既存の仕組みが外す** |
| 周期 | 10分ごと、起動15分後から |

### 途中で出した失敗

枠の歯止めを書く時、**実物を読まずに `usagePercent()` / `SCOUT_STOP_USAGE_PCT` と書いた**。
どちらも存在しない(正しくは `getLastRpcUsage()` と `SCOUT_QUOTA_STOP_PCT`)。
§9 の「実物を読まずに書く」を**また**やった。`node --check` は通ってしまうので、
**grep で呼び出し先の実在を確かめてから書く**。

### 次に見る数字

`経路なしの組[N組 計M件 上位 …]` と `組を足す[調べたN組 追加M本 無しK]`。
**足した後に `経路なし` が減り、`値付け` が増えるか**が答え。
減らなければ、その組は**そもそもDEXにプールが無い**(UniswapX の RFQ で
マーケットメーカーが直接埋めている)ということで、それも1つの答えになる。

## 11. 「$18.55」に水増しの穴が見つかった(2026年9月22日 23:55 JST、**オーナーの指摘**)

オーナーから「その利益は幻ではないか」と問われ、**自分の読み取りコードを疑った**ところ、
`extractSwap` に穴があった。

### 何が間違っていたか

```js
// 直す前:出力の中で**いちばん大きい1つ**だけを「ユーザーの取り分」として比べていた
let main = null;
for (const o of outputs) { if (amt > main.amount) main = {...}; }
return { amountOut: main.amount };   // ← 残りの出力を無視
```

**UniswapX の注文は、ユーザーへの出力に加えて「手数料の出力」を持つことがある。**
約定させる側は**その全部を届ける義務がある**。最大の1つだけを見ていると、
残りを**タダでもらえる前提**になり、その分そのまま**我々の取り分が水増しされる**。

### どれだけ効くか(算数)

| 注文 | 記録した利益 | 手数料0.15% | 0.25% | 0.50% |
|---|---|---|---|---|
| $1,901 | $3.3986 | $0.55 | **−$1.35** | **−$6.11** |

**9勝 合計$18.5477(平均注文$1,900と仮定):**

| 手数料 | 見落としていた額 | 実際は |
|---|---|---|
| 0.15% | $25.65 | **−$7.10** |
| 0.25% | $42.75 | **−$24.20** |
| 0.50% | $85.50 | **−$66.95** |

**手数料がたった0.15%あるだけで、符号が反転する。**

### 直したこと

- 比べる相手を「最大の1つ」から **出力の合計**に変えた
- **別の通貨での出力があるものは捨てる**(値段を付けられないものを
  「タダでもらえる」ことにしない)
- 出力が2つ以上あった件数と、**見落としていた額の合計**をログに出す
  → `出力複数N件(見落としていた額 計$X)`
- **保存の版番号を1→2に上げ、版1の数字を捨てた**
  (9勝$18.5477 は水増し込みで計算されている。読み戻すと汚染が残る)

### まだ分かっていないこと

**base の注文が実際に複数出力を持つのかは、まだ測っていない。**
持たなければ $18.55 はそのまま、持てば上の表のとおり反転する。
**次の計測が答える。** それまで $18.55 を利益と呼ばない。

### 教訓

今日、模型を疑う仕組み(チェーンでの確認)と、値動きを疑う仕組み(齢のふるい)は作った。
だが **「相手の額をそもそも正しく読めているか」は疑っていなかった。**
チェーンに確認しても、**比べる相手が間違っていれば意味がない。**

## 13. UniswapX は**チェーンごとに競売の方式が違う**(2026年9月23日 02:40 JST、調査のみ・コード変更なし)

`確認済 N勝 $X` を「取れるお金」と読めるかどうかは、**競売の方式**で決まる。
これまでの文書には方式の記録が無かったので、一次情報(UniswapX の GitHub の README と
`PriorityOrderReactor.sol`)で確かめた。公式の開発者文書は手元のプロキシで遮断されて読めなかった。

### どのチェーンに何があるか(README の配置表)

| チェーン | 反応器 | 競争の型 |
|---|---|---|
| **base** | **Priority Order Reactor** `0x0000…De729` **と** V3 Dutch `0x0000…27ba0` の**2つ** | 優先手数料の競売 / ブロックごとの値下がり |
| arbitrum | V3 Dutch `0xB274…a87c` のみ | ブロックごとの値下がり。**RFQ も独占期間も無い**(検索結果の公式文書の抜粋) |
| polygon / optimism / avalanche | V3 Dutch のみ | 同上 |

### base の Priority 注文は「速さ」の勝負ではない

`PriorityOrderReactor.sol` の実物:
- `block.number < auctionStartBlock` の間は `OrderNotFillable` で**誰も埋められない**
- 優先手数料 = `tx.gasprice − block.basefee − baselinePriorityFeeWei`
- ユーザーへの出力は `outputs.scale(priorityFee)` で**優先手数料に比例して増える**
  (1 wei あたり `mpsPerPriorityFeeWei` ミリbps)

つまり**全員が同じブロックに入札し、いちばん高い優先手数料が勝つ**。
順番は優先手数料で決まり、**「先に着いた者」ではない**。
これは我々に**向いている**。我々は速さでは負けるが(§8-1)、この形なら勝敗を決めるのは
**「どれだけ良い経路を持っているか」= 値付けの質**で、ここは既存のエンジンが効く。

さらに、**計測が出している差(我々の受取 − ユーザーが実際に受け取った額)は、
この型ならほぼそのまま「上乗せして勝てた余地」になる**。勝者より少しだけ多く
ユーザーに渡せば勝てるので、取り分 ≈ 差 − 上乗せ分 − ガス代。

### arbitrum の V3 Dutch は、差がそのまま取り分にはならない

値はブロック(250ms)ごとにユーザーに不利な側へ下がり、**最初に黒字になった者が先着で埋める**。
実際の約定ブロックで我々に差があったなら、**我々の損益分岐はもっと早いブロックに来ていた**
= 勝てた可能性は高い。だが取れる額は「そこから勝者が動くまでの数ブロックぶん」で、
**差の全額ではない**。しかも arbitrum は **Timeboost で我々に200msの遅延**がある(§8-1)。
250ms のブロックに対して200msの遅れは**ほぼ1ブロック**で、**先着勝負ではかなり不利**。

→ **arbitrum の `$16.07` は「勝てたかもしれない回数」の証拠であって、金額は上限にすぎない。**

### まだ分かっていないこと(推測で埋めない)

1. **base の標本が Priority 注文か V3 Dutch 注文か分からない。** 計測は
   `orders?chainId=…&orderStatus=filled` で**種類を指定せず**取っており、種類をログに出していない。
   どちらが混ざっているかで `$10.78` の読み方が変わる
2. **決済額のキーがどれで読めているか分からない。** `pickAmount` は
   `settledAmount → filledAmount → amount → startAmount` の順に拾う。`startAmount` に落ちた
   注文は**我々に不利な側**(勝ちを小さく見る)なので水増しにはならないが、数字の意味は変わる
3. 齢の判定は **base 若2/古4、arbitrum 若1/古5**(02:28 時点)。**若い側が足りない**

### 次に要るもの(提案。オーナーの判断待ち)

| # | 何を | 変更の種類 | 効き目 |
|---|---|---|---|
| A | 計測のログに**注文の種類**(API の `type` 等)と**使った金額キー**を出す | 計測だけ(送信経路に触れない) | 上の1と2が分かる。**base を Priority に絞って測れる** |
| B | `UNISWAPX_PROBE_INTERVAL_MS` を 120000 → **60000** | 環境変数のみ | 齢中央が73〜80秒 = 取得の遅れが約15〜20秒。60秒ごとなら齢が概ね15〜80秒に散り、**若い側が溜まる**。30秒にすると今度は古い側が溜まらない |

**どちらもお金のリスクは増えず、月額費用も増えない。** ただし B は再デプロイになり、
このデプロイ以降の数字(`実行` `内訳` など)がゼロに戻る(保存している計測は残る)。

## 14. UniswapX の「判断材料」を注文ごとに実測する(2026年9月23日、**オーナーの指示**)

> 「実際にどのぐらい速さが必要か、手数料がどのぐらい必要になるかの計算は、しっかり測ってください。
> でないとデータを蓄積している意味がない」

それまでの計測は「今の価格で比べて勝ち負けを数える」だけで、**この2つの問いに答えられない作り**だった。
注文1件ごとに、次を**実測**して記録する。

| 項目 | 何から測るか | 答える問い |
|---|---|---|
| **勝者の速さ** `delayBlocks` | `fillBlock − cosignerData.decayStartBlock`。1ブロックの実時間も約定時刻から実測 | どれだけ速ければよいか |
| **勝者のガス代** `gasUsd` | 勝者の約定取引のレシート(`gasUsed × effectiveGasPrice + l1Fee`)÷ その取引の `Fill` 数 | 手数料にいくらかかるか |
| **約定直前の我々の額** `gapBps` | **約定ブロックの1つ前の状態**で、我々の V3 経路をチェーンに見積もらせる | 値動きの汚染なしに、我々は何bps足りないか |
| **同じブロックで出せたら** `sameBlockNetUsd` | 我々の額 − 実額 − ガス代 | 勝者と同じ速さなら、いくら残ったか |
| **黒字化に要る差** `leadBlocks` | 値の曲線を再現(`NonlinearDutchDecayLib` と同じ手順、開始額は cosigner の上書き優先)し、ガス込みで我々が黒字になる最初のブロックを探す | 何ブロック早ければ勝てたか(+)/ 最後まで赤字か(null) |
| **勝者の顔ぶれ** `filler` | レシートの `Fill` イベント(`filler` は indexed) | 相手は何者で、何者が何割取っているか |

- 生存ログ(毎分):`[UniswapX判断] <chain> 判断材料N件 勝者の速さ[…] 勝者のガス[…] 約定直前の我々−実額[…] 同じブロックで出せたら黒字N件 …`
- 明細:`uniswapx-decisions-YYYY-MM-DD.jsonl`(1件1行・生の値。後から別の切り口で分析し直せる)
- **測れなかった件数も出す**:`測れず[V2経路 曲線 過去の状態 レシート 価格]`。
  特に「過去の状態」はノードが古いブロックの状態を持っていないと測れない。多ければ別の手段を考える

**読み方(判断の基準):**
- `同じブロックで出せたら黒字` が**2割を超え**、合計額が1日換算で意味のある額 → フィラーを作る価値がある。
  要る速さは `勝者の速さ` で決まる
- `約定直前の我々−実額` の中央が −数bps → 経路の改善(分割・取引所の追加)で届く
- −20bps 前後 → 経路では届かない(勝者は在庫や別の流動性を持つ)。§「届かせる方法」の③④になる

### §14 の追記(2026年9月23日 12:40 JST)— 初回2件で見えたことと、足したもの

初回の判断材料(base 2件):**勝者は値下がり開始の2ブロック(実測1ブロック2秒 = 約4秒)前に埋めていた**。
開始前 = ユーザーに最も有利な開始額のまま約定している。V3 Dutch では cosigner が `exclusiveFiller` を
指定すると、`decayStartBlock` まで**その者しか埋められない**(他者は `exclusivityOverrideBps` 分を上乗せすれば横取り可)。
勝者が独占者(= RFQ に勝った quoter)なら、**速さを磨いても勝てず、quoter になる(審査)ことが条件**になる。

足したもの(PR #152):
- `独占[あり N件 独占期間中に約定 M件 独占者本人が埋めた K件 横取りの上乗せ中央 Xbps]`

- `取消[健全(式のずれ?)]` が出る → 健全度の式が Morpho とずれている。**数字を信じる前に直す**
