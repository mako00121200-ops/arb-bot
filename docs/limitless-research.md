# Limitless Exchange(BTC/ETH 時間足 Up/Down)自動売買の事前調査

調査日: 2026年9月19日 / 対象: https://limitless.exchange(Base, chainId 8453)

> この調査は既存のDEX裁定bot(arb-bot本体)とは別テーマ。本番コードには一切手を入れていない。

## 0. 結論(先に要点だけ)

| 論点 | 結論 |
|---|---|
| 日本から行えるか | **技術的・規約的には可能**(日本は禁止国リストに無い、KYC無し、ウォレットとAPIキーだけ)。ただし**法的にはグレー**で、利用者側に賭博罪リスクが残る。詳細は §1 |
| バイナンス/バイバイで先読みできるか | **「オラクルの先読み」としては使えない**。決済オラクル(Pyth Pro)の対Binance遅延は p99 で約70ms、時にマイナス。**板の気配より速い情報源にはならない**。ただし**σ推定・板の厚み・約定フロー**の材料としては必須。詳細は §2 |
| 速度は影響するか | **する。ただし「テイク速度」ではなく「キャンセル速度」**。Limitlessには**テイカー・ディレイ(速度制限)**が実装されており、テイカーの一撃必殺は構造的に潰されている。**有利な席はメイカー側**。詳細は §3 |
| 運営の判定方法 | **Pyth Pro(旧Lazer)の BTC/USD を毎時ちょうどに1点サンプリング**し、前の時刻より「厳密に高ければ Up、それ以外は Down」。同値は Down。短期クリプト市場は Chainlink Data Streams も併用。詳細は §4 |
| 一番利益が出そうな戦略 | **①寄り付きのオラクル乖離を取る → ②理論価格モデルによるメイカー専業(手数料0 + リベート + LP報酬)**。ラストセカンドのスナイピングは本命にしない。詳細は §6 |

**この環境からは limitless.exchange / docs.limitless.exchange に直接アクセスできなかった**(ネットワークポリシーで遮断)。
そのため「◎実測」= 公式SDKのソースコードを直接読んで確認、「○三次情報」= 検索結果経由、と確度を分けて記載する。
○の項目は、実際にAPIキーを取って自分で叩き直すまで確定としないこと。

## 1. 日本から行えるか

### 1-1. 規約とシステム面: 可能 ○

- 利用規約上のアクセス禁止国は **ロシア・ベラルーシ・キューバ・イラン・北朝鮮・シリア・クリミア/ドネツク/ルハンスク**。
- **取引禁止国は アメリカ合衆国 と "Republic of China"** の2つ。
- **日本はどちらのリストにも入っていない。**
- ウォレット接続のみでKYCは不要。担保は Base 上の USDC。
- APIキー(`lmts_...`)は UI のプロフィールメニューから発行。ここだけは一度ブラウザ操作が要る(iPhoneでも可)。

### 1-2. 日本法: グレー。ここが最大のリスク

私は弁護士ではないので、実行前に専門家に確認してほしい。調べた範囲での整理:

**(a) 賭博罪(刑法185条)ルート**
- 単純賭博罪は50万円以下の罰金または科料。常習賭博は3年以下の拘禁刑。
- オンラインカジノについては、実際に**利用者側が摘発・罰金刑を受けた事例がある**。
- 予測市場が賭博に当たるかは**日本で判例が無く未確定**。国内の法律事務所・シンクタンクの論考でも「グレー〜違法の可能性が高い」という評価が主流。

**(b) 金商法(店頭デリバティブ)ルート**
- 価格の騰落を二者択一で当てる取引は、典型的には**店頭バイナリーオプション=店頭デリバティブ**に該当する。
- 日本居住者に業として提供するには金融商品取引業の登録が必要で、**無登録での提供は運営者側が違法**。
- この構成なら**利用者側は原則として処罰されない**(被害者側の扱い)。

**(c) なぜ国内FXや先物は賭博にならないのか**
- 金融法委員会の論点整理によれば、店頭デリバティブは「**金融商品取引業者等が当事者または媒介者である場合**」に賭博罪の適用が除外される、という整理になっている。
- **Limitless は登録業者ではない**ので、この適用除外には乗らない。つまり(a)のルートが消えない。

**(d) 実務上の副次リスク**
- Bybit は2026年に**日本居住者へのサービス提供終了**を発表済み。Limitless も将来同じ判断をする可能性があり、**その時に資金が引き出せるかが最大の運用リスク**。
- 常に「口座に置く額 = 失ってもいい額」に抑え、利益は都度 Base から出金する運用にすべき。

**(e) 税**
- 暗号資産の売買益と同じく**雑所得・総合課税**になる見込み(申告分離ではない)。住民税込みで最大55%。
- **手残りベースで考えると、必要なエッジは表面利回りの約2倍必要**。この点は戦略の採算ラインに直結するので §6 に織り込む。

### 1-3. 実行場所は日本である必要が無い

botは Railway 等のクラウドで動かすので、**botの所在地と本人の居住地は別問題**。
ただし「日本居住者が操作している」事実は変わらないので、1-2のリスクはVPS等では消えない。ここを誤魔化す構成は取らない。

## 2. バイナンス/バイバイによる「価格の先読み」は使えるか

### 2-1. オラクルの先読みとしては使えない ○

- 決済に使われる **Pyth Pro(旧 Pyth Lazer)** は、取引所・マーケットメイカーなど**120社以上のファーストパーティ発行者**から直接価格を取っている。
- 公表されている**対Binanceのエンドツーエンド遅延は p99 で約70ms、時にマイナス**(=Binanceの板に出るより早いことがある)。
- 更新頻度は 1ms / 50ms / 200ms のチャネルがある。
- つまり **「Binanceを見てオラクルの動きを先回りする」余地はほぼゼロ**。むしろPyth側が先行し得る。

### 2-2. それでもCEXデータは必須 ◎

先読みではなく、**モデルの入力**として要る。オラクルは「価格1点」しかくれないため:

| 用途 | Pyth(Limitless WS) | Binance/Bybit/OKX 公開WS |
|---|---|---|
| 決済に使われる価格そのもの | ○ これが正 | × |
| 板の厚み・板の偏り | × | ○ |
| 約定フロー(テープ) | × | ○ |
| σ(ボラ)の推定 | △ 粗い | ○ 1秒足以下で作れる |
| 先物のベーシス・資金調達率 | × | ○ |

- **公開マーケットデータはアカウント不要**。Binance は `data-stream.binance.vision` でAPIキー無しに読める。Bybitの公開WSも同様。
  → **Bybitの日本居住者向けサービス終了は、データ参照だけなら影響しない**。
- 数秒先の方向を当てる材料として現実的に効くのは、**板の偏り(order book imbalance)と成行フローの符号**。ただし効果は「数秒だけ・弱い」ので、これ単独で勝てる想定はしないこと。

### 2-3. 本当の「先読み」はどこにあるか

CEXの先読みではなく、**「板 vs 理論価格の乖離」が実質的なエッジ**。§5・§6 で扱う。

## 3. 速度は影響するか

### 3-1. テイカー・ディレイ(速度制限)が実装されている ◎実測

公式TypeScript SDKのソースに明記されていた(`src/types/orders.ts`):

```
'DELAYED' means the taker order was accepted but is held by a
per-market taker delay before being released to the matching engine
(see `eligibleAt`).
```

- 注文レスポンスの `execution.settlementStatus` が `DELAYED` のとき、`execution.eligibleAt` に**「マッチングエンジンに解放される時刻」**が入る。
- **市場ごとに遅延時間が設定される**(per-market)。
- メイカー側にこの遅延は無い(CHANGELOG: MATCHEDフレームで「Maker side reports a 0 fee estimate」、遅延はテイカー注文の話)。

これは IEX のスピードバンプと同じ**非対称スピードバンプ**で、目的は明確に**レイテンシ裁定(=板の食い逃げ)の無力化とメイカー保護**。

### 3-2. したがって速度の意味が逆転する

| 立場 | 速度の効き方 |
|---|---|
| テイカー(スナイパー) | 速くても**遅延の分だけ待たされる**。その間にメイカーは気配を引ける。**構造的に不利** |
| メイカー | **キャンセルの速さが全て**。テイカー・ディレイは「陳腐化した自分の指値を取り消すための猶予時間」そのもの |

**→ テイカー・ディレイの実測値が、この案件で一番重要な未知数。**
- 遅延が例えば 500ms なら、東京から往復250msでも間に合う=日本から動かしても戦える。
- 遅延が 50ms なら、**APIサーバの近くに置かないとメイカーは務まらない**。

測り方(小額でできる):
1. 板から確実に外れる価格でFOKを1枚投げる。
2. レスポンスの `execution.settlementStatus` と `eligibleAt` を見る。
3. `eligibleAt - 送信時刻` が遅延。市場種別(1時間足BTC / 日足 / スポーツ)ごとに測る。

### 3-3. ネットワーク遅延

- REST: `https://api.limitless.exchange` / WS: `wss://ws.limitless.exchange`
- マッチングは**オフチェーンのエンジン(OME)**、決済がBase上。したがって**Baseのブロックタイム(2秒)は板の勝負には効かない**。効くのは純粋にAPIサーバまでのRTT。
- ホスティング先は未確認。**Railwayの各リージョン(us-west / us-east / europe-west / asia-southeast)から `api.limitless.exchange` へのRTTを実測して一番近い所に置く**のが先決。

## 4. 運営側の判定方法

### 4-1. 決済ルール ○

実際の市場ページの文言:

> 「2026年7月26日 08:00 UTC の Pyth Pro BTC/USD の価格が、2026年7月26日 07:00 UTC の Pyth Pro BTC/USD の価格より **厳密に高ければ(strictly higher)** Up に決済。それ以外は Down に決済。」

ここから読み取れること:

1. **毎時ちょうどの1点サンプリング**。平均でもVWAPでもない。
2. **同値は Down**。イコール時はNO側が勝つ(構造的な微小バイアス。実質無視できるが、タダなので拾う)。
3. 行使価格(前の時刻の価格)は、APIの **`openPrice`** フィールドで取れる ◎実測(`src/types/markets.ts`: "Opening price for oracle markets")。
4. 市場のオラクル情報は **`priceOracleMetadata`**(`ticker` / `assetType` / `pythAddress` / `symbol`)で取れる ◎実測。
5. 短期クリプト市場は **Chainlink Data Streams** でも決済されている(2026年6月導入、週約19,000市場)。**市場ごとにどちらか、ルール文言を必ず読むこと。**
6. スポーツ・政治などのカスタム市場は運営が手動で24〜72時間以内に決済(今回は無関係)。

### 4-2. 1点サンプリングであることの実務的な意味(重要)

- **満期時にオラクルが一瞬ヒゲを出すと結果が反転し得る**。`|現在値 − openPrice|` がオラクルのノイズ幅程度しか無いときに満期を迎えるのは、**手数料を払ったコイントス**でしかない。
  → **ルール: `|z| < 一定値` の状態で満期をまたがない**(§6で数値化)。
- 逆に、**寄り付き(`openPrice`)も1点サンプリング**。ここでオラクルがヒゲを出していると、**行使価格が「今の実勢」からずれた状態で市場が始まる**。
  → これが後述の最有力エッジ(§6-A)。
- 決済価格操作の論文も出ているが、資金規模的に自分が仕掛ける話ではない。**他者が仕掛けてくる側**として、満期直前の薄い板は信用しないという守りに使う。

## 5. この市場の理論価格

1時間 Up/Down は、**行使価格 = `openPrice`、満期 = 毎時0分のバイナリーコールオプション**そのもの。

```
p_up = Φ( ln(S_t / openPrice) / (σ * sqrt(τ)) )

  S_t : 現在のオラクル価格
  σ   : 1時間あたりのボラティリティ(対数)
  τ   : 残り時間(時間単位, 例: 残り15分 → 0.25)
  Φ   : 標準正規分布の累積分布関数
```

ドリフトとボラドラッグは1時間スケールでは無視してよい。

### 感度表(年率σ=40%、BTC=$100,000 の場合)

1時間の1σ = 0.427% = **約 $427**

| 残り時間 | 1σ(USD) | Δ=+$100 | Δ=+$200 | Δ=+$400 |
|---|---|---|---|---|
| 60分 | $427 | 59.3% | 68.0% | 82.5% |
| 30分 | $302 | 63.0% | 74.6% | 90.7% |
| 15分 | $214 | 68.0% | 82.5% | 96.9% |
| 10分 | $174 | 71.7% | 87.4% | 98.9% |
| 5分 | $123 | 79.1% | 94.8% | 99.9% |
| 2分 | $78 | 90.0% | 99.5% | ≒100% |
| 1分 | $55 | 96.5% | ≒100% | ≒100% |
| 30秒 | $39 | 99.5% | ≒100% | ≒100% |

読み方:
- **満期1〜2分前には、Δ が±$100程度あればほぼ勝負がついている**。ここが「ラストセカンド・スナイピング」の狙い目だが、§3の通りテイカー・ディレイで潰されている前提で設計する。
- **σの誤差がそのまま値付けの誤差になる**。σを年率30%と50%で置くだけで、残り15分・Δ=$200 のとき 82.5% が 87.9%〜78.6% と 10ポイント近く動く。**σ推定の質がこの戦略の心臓部**。

### 手数料 ○

| 区分 | 料率 |
|---|---|
| メイカー(指値) | **0%** |
| テイカー 買い | 0.40% 〜 3.00%(**低確率ほど高い / 高確率ほど安い**) |
| テイカー 売り | 0.42% 〜 1.50%($0.50 付近が最大、両端で低下) |
| AMM市場 | 一律 0.40% |
| 短期クリプト市場のメイカー | **テイカー手数料の100%が日次USDCリベートとして還元**(=実質マイナスコスト) |

- 板は **YESトークンの1本の板**(`OrderBook.tokenId` は YES) ◎実測。
  → **「YES買い」と「NO買い」は同じ板の裏表**なので、**1市場の中で YES+NO < $1 のノーリスク裁定は存在しない**。これは期待しないこと。
- Conditional Tokens (CTF) は Base の `0xc9c98965297bc527861c898329ee280632b76e18`(Gnosis標準)。split/merge は可能だが、上記の理由で単独市場の箱裁定には使えない。

## 6. 戦略提案

**大前提: テイカーで殴りに行く設計にしない。Limitlessは構造的にメイカーを勝たせる設計になっている。**

### A. 【本命1】寄り付きのオラクル乖離を取る

**仮説**: `openPrice` は毎時0分ちょうどの1点サンプリングなので、オラクルが一瞬ヒゲを出した時刻に確定すると、**行使価格が実勢からズレた状態で市場が始まる**。
一方、板は「新しい市場だからとりあえず0.50」で立ち上がりやすい。この差が初手のエッジ。

- 寄り付き直後(τ≒1)に `p_theo = Φ(ln(S_t/openPrice)/σ)` を計算。
- 例: `openPrice` が実勢より $80 低く刻まれていたら、開始直後の真の `p_up` は Φ(80/427) = **57.4%**。板が 0.50 なら **7セントの乖離**。
- **BTCとETHで1日24回ずつ、計48回/日**発生し得る。レースに勝つ必要が無く、寄り付き直後の数秒〜数十秒あればよいので**日本からでも取れる可能性がある**。
- 実行は原則メイカー(`postOnly` のGTC)で置く。埋まらなければ捨てる。乖離が大きい時だけFAKでテイク。

**検証方法**: §7のデータ収集で「寄り付き時の `ln(S_t/openPrice)` の分布」と「寄り付き直後の板の中値」を並べる。ここに相関が無ければ仮説は棄却。**先に測ること。**

### B. 【本命2】理論価格モデルによるメイカー専業

収益源が3本ある:

1. **スプレッド**: 理論価格の両側に指値。手数料0%。
2. **テイカー手数料100%リベート**(短期クリプト市場) ○要検証。プラットフォーム出来高が日次$35〜40M規模なので、短期クリプト市場だけで日次数万ドル規模のテイカー手数料がメイカーに還元されている計算になる。**ここが実は最大の収益源かもしれない**。
3. **LP報酬**: 市場ごとに `dailyReward` / `maxSpread` / `minSize` / `rewardsEpoch` / `c` / `rebateRate` がAPIで取れる ◎実測。**中値に近く、かつ `maxSpread` 以内・`minSize` 以上**の指値が対象。毎分計算、日次 22:30 UTC 払い ○。
   - ただしLP報酬プール自体は日次$1,000程度という報告もある ○。**過度に期待せず、2のリベートを主軸に見積もること。**

**守り(これが本体)**:
- オラクル価格が動いたら**即座に指値を引き直す**。テイカー・ディレイが猶予時間(§3-2)。
- 在庫上限と`|z|`上限を決め、**`|z|` が大きくなった(＝勝負がついた)市場からは指値を全部引く**。逆選択はここで発生する。
- **満期をまたぐポジションを原則持たない**。持つなら `|z| > 3`(ほぼ確定)のときだけ。

### C. 【補助】理論からの乖離テイク

- `|p_theo − p_book| − テイカー手数料 > 閾値` のときだけ FAK(価格指定・残りは即キャンセル)でテイク。
- 高確率側(0.90超)の買いはテイカー手数料が0.40%まで下がるので、**取るなら favourite 側**。低確率側の買いは手数料3%で潰されるので手を出さない。
- テイカー・ディレイがあるので**約定率は低い前提**。ヒット率を実測して、割に合わなければ切る。

### D. 【将来】会場間裁定

- Polymarket にも同一の 1時間 BTC Up/Down がある。Kalshi にもあるが**米国限定なので日本からは不可**。
- Limitless と Polymarket で、**同一時刻・同一原資産・同一行使価格**なら価格差は直接の裁定機会。
- ただし両方に資金を置く必要があり、決済オラクルが違えば同一資産ではない。**Aとbが回ってからの話**。

### 採算ラインの目安

税(雑所得・最大55%)を考えると、**税引前で年率換算20%を割るなら、時間と資金を別の所に使ったほうがいい**。
初期検証では「日次のPnLが取引コストとインフラ費($20〜50/月)を上回るか」だけを見る。

## 7. 今すぐには出来ないこと / 何があれば出来るようになるか

| # | 足りないもの | 何をすれば埋まるか | 難易度 |
|---|---|---|---|
| 1 | **Limitlessのアカウントとメイカー用の資金** | ウォレット接続 → プロフィールメニューでAPIキー(`lmts_...`)発行 → Base に USDC を送金。CTF Exchange への approve が1回必要(BUYはUSDC→`venue.exchange`、SELLはCT→`venue.exchange`)。**アドレスはハードコードせず `GET /markets/{slug}` の `venue` から取る**(公式が明示的に警告) | 低(iPhoneで可) |
| 2 | **テイカー・ディレイの実測値** | 小額FOKを投げて `execution.eligibleAt` を記録。市場種別ごとに。**これが戦略の可否を決める** | 低 |
| 3 | **自前のティックデータ** | 公式の `GET /markets/{slug}/historical-price` は **最小粒度が1時間足**で、1時間市場の中の動きは一切見えない。**WSを24時間回して自分で貯めるしかない**。`wss://ws.limitless.exchange` の `subscribe_market_prices` は**APIキー不要**で `orderbookUpdate` と `oraclePriceData` が取れる ◎実測 | 中(2〜3週間の収集期間が要る) |
| 4 | **σ(ボラ)推定器** | Binance/Bybit の公開WS(アカウント不要)から1秒足を作り、EWMA/HARで1時間σを推定。直近の実現ボラと時間帯効果(アジア時間は薄い)を入れる | 中 |
| 5 | **低遅延なホスティング先** | Railwayの各リージョンから `api.limitless.exchange` へRTTを実測し、一番近い所にデプロイ。#2の遅延値と比較して「メイカーが務まるか」を判定 | 低 |
| 6 | **リベート/LP報酬の実額確認** | `GET /portfolio/points` と `GET /portfolio/positions` の `rewards` を毎日記録。小額でメイカーを1週間回せば実額が出る | 低 |
| 7 | **法務・税務の確認** | 弁護士に「日本居住者が海外の予測市場で自動売買する場合の賭博罪該当性」を確認。税理士に雑所得の申告方法(1時間ごとの大量約定の集計)を確認 | 外部依存 |
| 8 | **リスク上限とキルスイッチ** | 1市場あたりの最大在庫、日次最大損失、オラクル/WS切断時の全キャンセル。**これが無いまま実弾を入れない** | 中 |

### 現実的な進め方(提案)

```
第1段階(資金ゼロ, 2〜3週間)
  WSでティックを貯める + 理論価格を毎秒計算して「板との乖離」をログに残すだけ。注文は出さない。
  → 戦略Aの仮説が正しいか、板がすでに効率的かが、ここで判明する。

第2段階(少額 $200〜500, 2週間)
  テイカー・ディレイ実測 + メイカー指値を1市場だけで回す。
  → リベートとLP報酬の実額を確定させる。

第3段階(条件付きで増資)
  第1段階のログで乖離が有意、かつ第2段階でリベートが実在するなら、市場数と資金を段階的に増やす。
```

**第1段階は資金も法的リスクもゼロ**(公開WSを読むだけ)で、そこで戦略の当否が8割判明する。ここから始めるのが一番損が小さい。

## 10. 第1段階の実装(2026年9月19日)

`limitless/collector.js` を追加した。**注文は出さない観測専用**で、本番botとは依存も起動も別(`limitless/package.json`、Railwayでは別サービス)。
動かし方と確認手順は `limitless/README.md`。

### 書く前に見直して直した点

- **WSは生のWebSocketではなく socket.io(EIO=4、namespace `/markets`)** だった。公式SDKの `src/websocket/client.ts` で確認。生の `ws` で書いていたら1バイトも受け取れなかった
- **slugの数字は市場の開始時刻(Unix秒)**。`btc-up-or-down-hourly-1785049200` = 2026-07-26 07:00 UTC 開始、08:00 決済。新市場は `GET /markets/active/slugs`(認証不要)と `subscribe_market_lifecycle` の `marketCreated` の両方で拾う
- 購読解除チャネル `unsubscribe_market_prices` は SDK の一覧に**無い**。決済済みの市場は無視するだけにした
- `oraclePriceData` が1時間市場で流れるかは**未確認**。流れなければ Pyth Hermes(公開・キー不要)と Binance を参照価格に使う。どれを使ったかは `theo` 行の `src` に残る
- σ推定器は「最初の120サンプルは単純平均、以降EWMA(半減期10分)」。EWMAだけだと立ち上がりが遅い(自己診断で発覚し修正)
- Hermes / Binance の受信形式はこの環境から確認できなかったので、**各イベントの最初の1件を `raw_sample` に生で残す**ようにした。起動後10分のログで形式を照合する

### この段階で答えが出る問い

| 問い | 見る場所 |
|---|---|
| 戦略A(寄り付きの乖離)に信号があるか | `[要約]` 行の「理論5sが正解側」と「板5sが正解側」の的中率の差。理論が板より当たっていれば信号あり |
| 板は既に効率的か | `theo` 行の `edgeBuyYes` / `edgeSellYes` の分布。常に0付近なら手が無い |
| 決済価格は Limitless から取れるか | `raw_sample` に `ws:oraclePriceData` があるか |
| どれくらいの頻度で板がズレるか | `edge` が閾値(例: 0.02)を超えた秒数 / 全体 |

- この環境からは api/ws.limitless.exchange、Hermes、Binance の全てが遮断されているため、**動作確認は Railway 上で行うしかない**。自己診断(`npm run selftest`)と、外部が全部落ちてもクラッシュしないことだけ確認済み

## 11. 既存DEX裁定botからの流用マップ(2026年9月25日)

コードを読み直した結論: **実行部は流用できないが、運用の骨格はほぼ全部流用できる。**

### そのまま流用できるもの

| 既存の仕組み | Limitlessでの使い方 |
|---|---|
| `scripts/opportunity-journal.js` 記録簿(検出→判定→送信/見送り→結果) | 「理論価格→板→注文→決済結果」を同じ形式で。`summarize(hours)` もそのまま |
| `scripts/competitor-check.js` 「誰が取ったか」の30秒後答え合わせ | **テイカー・ディレイの実測に使う**。DELAYEDの間に板が消えた(メイカーに引かれた)/自分が取れた/誰も触らず、の分類は既存の `ours / other / moved / untouched` と同型 |
| `scripts/real-execution-log.js` 紙上と確定を分ける思想 | 事前の理論価格ではなく「決済でredeemした額 − 投入額」だけを確定利益にする |
| `scripts/trade-cap.js` 成功回数で段階的に上限を上げる | 1市場あたりの在庫上限に。フラッシュローンと違い自己資金が減るので必須 |
| `index.js` のダッシュボード(`renderPage` / `heartbeat`) | iPhoneで見る前提の作り。collectorにも同じ形の画面を足せる |
| Railway運用の型(全て環境変数、`RUN_…` フラグ、ログで確認する手順) | 別サービスとして同じ型で(`limitless/README.md`) |
| `chain-config.js` のBase設定、ガス見積もりの知見(baseFee+priority)、nonce直列化の教訓 | USDCのapprove・決済後のredeem・出金をBaseで打つ部分に |
| 「推測で決めない。実測してから広げる」「作業は1つずつ」 | 第1段階(観測)→第2段階(少額メイカー)→増資、の運用そのもの |

### 流用できないもの

| 既存の仕組み | 理由 |
|---|---|
| フラッシュスワップ+自作コントラクトの原子的実行 | 板はオフチェーン(socket.io + EIP-712署名)で、1トランザクションで閉じる裁定が無い。**Solidityの出番は無い**。将来のPolymarket裁定も両会場オフチェーンなので同じ |
| Sync/SwapのWebSocket受信 | 「受信→メモリ更新→即判定」の骨格は同じだが、socket.ioなので実装は別(collectorで済み) |
| 「速度で勝つ」設計 | 「指値を引く猶予で勝つ」設計に変わる |

### 既存の知見で特に効くもの

- 「投入$2で利益$24はハニーポット。本物は0.1〜0.5%」→ Limitlessでも「板が理論から10セント離れている」はまず自分のσかオラクルの解釈を疑う
- 「約1.5時間黒字0件。課題は速度より機会の数」→ Limitlessは1日48回の寄り付きがあり、機会の数が構造的に多い。DEX裁定と補完関係
- 資金面でも競合しない: DEX裁定はフラッシュローンで自己資金ほぼ不要、Limitlessは自己資金(USDC)が要る。同じRailwayプロジェクトで並走できる

### 進め方

```
第1段階(資金0)    collector をRailwayの別サービスに配置 → 2〜3週間観測
第2段階($200〜500) 記録簿・答え合わせ・段階上限を index.js から移植し、1市場だけメイカー指値
第3段階           1・2が黒なら市場数と資金を段階的に増やす。ダッシュボードを共通化
```
